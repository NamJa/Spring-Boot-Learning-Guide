API 버전 관리 (Spring Framework 7 내장)

지금까지 만든 Book API는 아직 아무도 쓰지 않는 API였습니다. 배포하는 순간부터는 사정이 달라집니다. 응답에서 필드 하나를 빼거나 이름을 바꾸는 것만으로도 이미 배포된 모바일 앱이 깨질 수 있습니다. 서버는 언제든 다시 배포할 수 있지만, 사용자의 휴대폰에 깔린 앱은 우리가 되돌릴 수 없습니다.

그래서 실무의 REST API는 거의 예외 없이 버전을 갖습니다. 그리고 Spring Boot 4(Spring Framework 7)부터는 이 버전 관리가 프레임워크 기본 기능이 되었습니다. 그전까지 각자 손으로 만들던 것을 이제 애너테이션 속성 하나로 처리합니다.

Spring Boot 4의 신기능입니다. 인터넷에 있는 Spring Boot 3 이하의 "API 버전 관리" 글은 전부 직접 구현하는 우회 방법(경로에 /v1 하드코딩, headers = "X-API-Version=1" 조건, 커스텀 RequestCondition)을 설명합니다. 아래에서 다루는 version 속성과 spring.mvc.apiversion.* 설정은 Spring Framework 7 / Spring Boot 4에서 새로 들어온 것이라 Boot 3에서는 동작하지 않습니다.

1. 버전을 붙이지 않으면 생기는 일

Book API의 응답에 할인가 필드를 추가하고, 동시에 price의 의미를 "정가"로 바꾸고 싶다고 해봅시다. 버전이 없으면 선택지는 둘뿐입니다.

2. 버전을 어디에 실을 것인가 — 네 가지 전략

클라이언트가 "나는 1.1 버전으로 이야기하겠다"를 서버에 알리는 방법은 네 가지입니다. Spring Boot 4는 넷 다 기본 제공하며, spring.mvc.apiversion.use.* 프로퍼티로 고릅니다.

전략 프로퍼티 요청 예 특징
요청 헤더 use.header X-API-Version: 1.1 URL이 깨끗하다. 가장 많이 쓰이는 기본값
쿼리 파라미터 use.query-parameter /api/books?version=1.1 브라우저 주소창·curl로 테스트하기 가장 쉽다
경로 세그먼트 use.path-segment /v1.1/api/books 눈에 보이고 캐시·라우팅에 유리. 인덱스(0부터)를 지정
미디어 타입 파라미터 use.media-type-parameter Accept: application/json;version=1.1 콘텐츠 협상과 한 몸. 가장 "REST 원리주의"에 가깝다

넷 중 하나만 고르세요. 여러 전략을 동시에 켜면 클라이언트마다 다른 방식을 쓰게 되고, 어느 쪽이 이겼는지 추적하기 어려운 버그가 생깁니다. 팀에서 하나를 정하고 문서에 못 박는 편이 낫습니다. 또한 Java 설정(WebMvcConfigurer)과 application.yml을 동시에 쓰지 마세요. 둘 다 설정하면 어느 쪽이 실제로 적용됐는지 읽는 사람이 알 수 없습니다.

application.yml로 설정하기 (권장)

Book API는 헤더 방식을 쓰겠습니다. Phase 1-05에서 만든 설정 파일에 다음을 추가합니다.

spring:
  mvc:
    apiversion:
      use:
        header: X-API-Version    # 이 헤더에서 버전을 읽는다
      default: "1.0"             # 헤더가 없는 요청은 1.0으로 취급
      required: false            # true면 헤더 없는 요청을 400으로 거절
      # supported: ["1.0", "1.1"]   # 매핑에 없는 버전까지 허용하고 싶을 때만
      # detect-supported: true      # (기본값) 컨트롤러의 version 속성에서 자동 수집

이것만으로 자동 설정이 ApiVersionStrategy 빈을 만들고 DispatcherServlet에 연결합니다. 자동 설정의 전형적인 모습입니다 — 프로퍼티 하나가 인프라 한 덩어리를 켭니다.

코드로 설정하기

조건부 로직이 필요하거나 커스텀 리졸버를 끼워야 한다면 WebMvcConfigurer를 씁니다.

package com.example.bookapi.config

import org.springframework.context.annotation.Configuration
import org.springframework.web.servlet.config.annotation.ApiVersionConfigurer
import org.springframework.web.servlet.config.annotation.WebMvcConfigurer

@Configuration
class ApiVersionConfig : WebMvcConfigurer {

    override fun configureApiVersioning(configurer: ApiVersionConfigurer) {
        configurer
            .useRequestHeader("X-API-Version")   // 또는 useQueryParam / usePathSegment / useMediaTypeParameter
            .setDefaultVersion("1.0")
            .setVersionRequired(false)
            .detectSupportedVersions(true)        // 기본값 — 매핑에 선언된 버전을 자동 수집
    }
}

3. 컨트롤러에 버전 붙이기

@RequestMapping과 @GetMapping·@PostMapping 등 모든 매핑 애너테이션에 version 속성이 생겼습니다. Book API에 1.1을 추가해 봅시다. 먼저 1.1에서 내려줄 새 표현을 DTO로 만듭니다.

package com.example.bookapi.dto

import java.time.LocalDate

// 1.1부터 내려주는 확장 표현 — 기존 BookResponse는 손대지 않는다
data class BookDetailResponse(
    val id: Long,
    val title: String,
    val author: String,
    val isbn: String,
    val price: Int,
    val publishedAt: LocalDate,
    val discountedPrice: Int,      // 1.1에서 추가된 필드
) {
    companion object {
        fun from(book: BookResponse): BookDetailResponse = BookDetailResponse(
            id = book.id,
            title = book.title,
            author = book.author,
            isbn = book.isbn,
            price = book.price,
            publishedAt = book.publishedAt,
            discountedPrice = (book.price * 0.9).toInt(),
        )
    }
}

이제 컨트롤러에 두 개의 매핑을 나란히 둡니다. BookService는 전혀 건드리지 않습니다 — 버전은 표현(presentation)의 문제이지 도메인의 문제가 아니기 때문입니다.

package com.example.bookapi.controller

import com.example.bookapi.dto.BookDetailResponse
import com.example.bookapi.dto.BookResponse
import com.example.bookapi.service.BookService
import org.springframework.web.bind.annotation.GetMapping
import org.springframework.web.bind.annotation.PathVariable
import org.springframework.web.bind.annotation.RequestMapping
import org.springframework.web.bind.annotation.RestController

@RestController
@RequestMapping("/api/books")
class BookController(
    private val bookService: BookService,
) {

    // 버전 미지정 — 모든 버전에 매칭되지만, 버전이 붙은 매핑이 있으면 그쪽에 밀린다
    @GetMapping("/{id}")
    fun getOne(@PathVariable id: Long): BookResponse =
        bookService.findById(id)

    // 1.1 이상 — 할인가를 포함한 확장 응답
    @GetMapping("/{id}", version = "1.1+")
    fun getOneV11(@PathVariable id: Long): BookDetailResponse =
        BookDetailResponse.from(bookService.findById(id))

    // ... 나머지 매핑은 Phase 2와 동일
}

4. 매칭 규칙 — 고정 · 베이스라인 · 미지정

version 속성에는 세 가지 형태를 쓸 수 있고, 여러 개가 동시에 조건을 만족하면 요청 버전 이하 중 가장 높은 것이 이깁니다.

표기 의미 언제 쓰나
version = "1.1" 고정 — 정확히 1.1 요청만 딱 그 버전에서만 존재했던 임시 동작
version = "1.1+" 베이스라인 — 1.1과 그 이상 전부 대부분의 경우. 새 동작을 도입한 시점을 표시
(속성 없음) 모든 버전에 매칭하되 가장 낮은 우선순위 버전 도입 이전부터 있던 기존 매핑

버전 문자열은 기본적으로 시맨틱 버전 파서(SemanticApiVersionParser)로 해석되므로 "1.1"과 "1.1.0"은 같은 값이고, "1.10" > "1.9" 처럼 숫자로 비교됩니다. 문자열 비교가 아닙니다. 날짜 기반 버전(2026-08-30) 같은 다른 체계를 쓰고 싶다면 ApiVersionParser를 직접 구현해 setVersionParser()로 끼웁니다.

5. 지원하지 않는 버전 · 빠진 버전

지원 버전 목록은 기본적으로 컨트롤러에 선언된 version 값들에서 자동으로 수집됩니다(detect-supported). 그 목록에 없는 버전이 들어오면 요청은 400으로 거절됩니다.

상황 예외 응답
지원하지 않는 버전 InvalidApiVersionException 400 Bad Request
버전은 유효하나 매칭되는 매핑이 없음 NotAcceptableApiVersionException 400 Bad Request
required: true인데 버전이 빠짐 MissingApiVersionException 400 Bad Request

세 예외 모두 ResponseStatusException을 상속하므로, Phase 4-02에서 만든 ProblemDetail 기반 전역 예외 처리에 그대로 얹힙니다. 별도 핸들러를 쓸 필요가 없습니다.

# 버전 없음 → default 1.0 → 기존 응답
curl -s localhost:8080/api/books/1

# 1.1 → 확장 응답
curl -s -H 'X-API-Version: 1.1' localhost:8080/api/books/1

# 지원하지 않는 버전 → 400 (ProblemDetail JSON)
curl -si -H 'X-API-Version: 9.9' localhost:8080/api/books/1 | head -1

6. 은퇴 예고 — Deprecation · Sunset 헤더

버전을 만드는 것보다 어려운 일이 버전을 없애는 것입니다. Spring Framework 7은 표준 헤더(RFC 9745 Deprecation, RFC 8594 Sunset)로 "이 버전은 언제 죽습니다"를 클라이언트에 자동으로 알려 주는 핸들러를 제공합니다.

package com.example.bookapi.config

import org.springframework.context.annotation.Configuration
import org.springframework.web.accept.StandardApiVersionDeprecationHandler
import org.springframework.web.servlet.config.annotation.ApiVersionConfigurer
import org.springframework.web.servlet.config.annotation.WebMvcConfigurer
import java.net.URI
import java.time.ZonedDateTime

@Configuration
class ApiVersionConfig : WebMvcConfigurer {

    override fun configureApiVersioning(configurer: ApiVersionConfigurer) {
        val deprecation = StandardApiVersionDeprecationHandler()
        deprecation.configureVersion("1.0")
            .setDeprecationDate(ZonedDateTime.parse("2026-09-01T00:00:00Z"))
            .setSunsetDate(ZonedDateTime.parse("2027-01-01T00:00:00Z"))
            .setDeprecationLink(URI.create("https://example.com/docs/api/migration-1.1"))

        configurer
            .useRequestHeader("X-API-Version")
            .setDefaultVersion("1.0")
            .setDeprecationHandler(deprecation)
    }
}

이제 1.0으로 들어온 요청의 응답에는 Deprecation·Sunset·Link 헤더가 자동으로 붙습니다. 클라이언트 팀에게 이메일 대신 응답 자체로 통보하는 셈이라, 로그·모니터링으로 "아직 1.0을 쓰는 클라이언트가 얼마나 남았는지" 추적하기도 쉬워집니다.

7. 버전별 테스트

테스트 전략에서 쓴 MockMvcTester로 버전 분기까지 검증합니다. 버전은 그냥 헤더이므로 특별한 API가 필요 없습니다.

package com.example.bookapi.controller

import com.example.bookapi.service.BookService
import org.assertj.core.api.Assertions.assertThat
import org.junit.jupiter.api.Test
import org.springframework.beans.factory.annotation.Autowired
import org.springframework.boot.webmvc.test.autoconfigure.WebMvcTest   // ⚠️ Boot 4에서 패키지 이동
import org.springframework.test.context.bean.override.mockito.MockitoBean
import org.springframework.test.web.servlet.assertj.MockMvcTester

@WebMvcTest(BookController::class)
class BookControllerVersionTest(
    @Autowired private val mvc: MockMvcTester,
) {
    @MockitoBean
    private lateinit var bookService: BookService

    @Test
    fun `버전이 없으면 기본 응답에 discountedPrice가 없다`() {
        // given: bookService.findById(1) 스텁 설정 …

        assertThat(mvc.get().uri("/api/books/1"))
            .hasStatusOk()
            .bodyJson().doesNotHavePath("$.discountedPrice")
    }

    @Test
    fun `1_1 요청에는 discountedPrice가 포함된다`() {
        assertThat(mvc.get().uri("/api/books/1").header("X-API-Version", "1.1"))
            .hasStatusOk()
            .bodyJson().extractingPath("$.discountedPrice").isEqualTo(32400)
    }

    @Test
    fun `지원하지 않는 버전은 400`() {
        assertThat(mvc.get().uri("/api/books/1").header("X-API-Version", "9.9"))
            .hasStatus(400)
    }
}

버전마다 테스트를 복제하지 마세요. 버전이 늘어날수록 테스트가 기하급수로 불어납니다. 실무에서는 "각 버전의 계약(응답 스키마)"만 버전별로 검증하고, 비즈니스 로직 테스트는 서비스 계층에서 버전과 무관하게 한 번만 작성합니다. 컨트롤러 버전 분기는 얇게 유지하는 것이 핵심입니다.

8. 실무 체크리스트

컨퍼런스 인사이트 (Spring I/O 2026, 바르셀로나). Spring Boot 4를 다룬 두 세션이 모두 API 버전 관리를 "직접 만들 필요가 없어진 대표적 기능"으로 꼽았습니다. Moritz Halbritter의 Inside Spring Boot 4: Restructuring for the Future는 자동 설정 모듈화·JSpecify 널 안정성·Jackson 3 전환과 함께 API 버전 관리를 4.x의 핵심 추가 기능으로 정리했고, Sébastien Deleuze의 Idiomatic Kotlin applications with Spring Boot 4는 2026년 Kotlin 서버 개발자가 챙길 항목 목록에 널 안정성·직렬화·관측성·복원력과 나란히 API 버전 관리를 올렸습니다.

정리

  • version 속성이 @RequestMapping 계열에 추가되어, 같은 경로를 버전별로 다른 메서드에 매핑할 수 있습니다. Spring Framework 7 / Spring Boot 4의 신기능입니다.
  • 버전 전달 방식은 헤더 · 쿼리 파라미터 · 경로 세그먼트 · 미디어 타입 파라미터 네 가지이며 spring.mvc.apiversion.use.*로 하나만 고릅니다.
  • "1.1+" 베이스라인 표기가 실무의 기본값입니다. 버전 미지정 매핑은 옛 클라이언트를 위한 안전망으로 남겨 둡니다.
  • 지원하지 않는 버전은 디스패치 단계에서 400으로 걸러지므로, 서비스 코드에는 버전 분기가 들어가지 않습니다.
  • StandardApiVersionDeprecationHandler로 은퇴 예고를 응답 헤더에 실어 보낼 수 있습니다.
