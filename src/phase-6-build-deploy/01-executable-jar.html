실행 가능 JAR 빌드

모든 배포는 하나의 실행 가능한 산출물에서 출발합니다. Spring Boot의 Gradle 플러그인은 애플리케이션 코드와 모든 의존성을 단일 jar에 담은 실행 가능 jar(흔히 fat jar 또는 uber jar)를 만들어 줍니다. 별도의 톰캣 설치 없이 java -jar만으로 내장 톰캣(Tomcat 11.0.24)을 띄우고 8080 포트에서 서비스가 시작됩니다.

이 문서에서는 Book API를 빌드해 산출물을 만들고, 그 내부 구조(특히 layered jar)를 이해하고, 실행 시 프로파일·인자·JVM 옵션을 주입하는 방법을 다룹니다.

bootJar로 빌드하기

Spring Boot Gradle 플러그인을 적용하면 bootJar 태스크가 자동으로 등록됩니다. Book API 프로젝트 루트에서 다음을 실행합니다.

# 실행 가능 jar만 빌드
./gradlew bootJar

# 전체 빌드 (컴파일 + 테스트 + bootJar + plain jar)
./gradlew build

산출물은 build/libs/ 아래에 생성됩니다.

$ ls -lh build/libs/
book-api-0.0.1-SNAPSHOT.jar        # 실행 가능 boot jar (의존성 포함)
book-api-0.0.1-SNAPSHOT-plain.jar  # plain jar (애플리케이션 클래스만)

버전 0.0.1-SNAPSHOT은 build.gradle.kts의 version 속성에서 옵니다. 파일명이 다르면 이후 명령의 jar 이름을 자신의 산출물에 맞춰 바꿔 주세요.

빌드된 jar는 다음과 같이 실행합니다.

java -jar build/libs/book-api-0.0.1-SNAPSHOT.jar

JDK 21(최소 17, 최대 26 지원)이 설치되어 있어야 하며, 실행 즉시 내장 톰캣이 기동되어 http://localhost:8080에서 Book API가 응답합니다.

plain jar vs boot jar

./gradlew build는 두 개의 jar를 만듭니다. 둘의 차이를 이해하는 것이 중요합니다.

구분 plain jar (-plain.jar) boot jar (실행 가능 jar)
포함 내용 우리 애플리케이션 클래스만 애플리케이션 + 모든 의존성 + 로더
실행 java -jar 불가 (의존성 없음) java -jar로 바로 실행
용도 다른 모듈이 라이브러리로 의존할 때 배포·실행용
Main-Class 없음 org.springframework.boot.loader.launch.JarLauncher

라이브러리로 쓸 일이 없다면 plain jar 생성을 끌 수 있습니다.

// build.gradle.kts
tasks.named<Jar>("jar") {
    enabled = false // plain jar 비활성화
}

실행 가능 jar의 내부 구조 (layered jar)

Spring Boot 4의 실행 가능 jar는 layered jar로 만들어집니다. 이는 jar 내부 콘텐츠를 변경 빈도에 따라 여러 계층으로 나눈 구조입니다. jar tf로 들여다보면 다음과 같은 레이아웃이 보입니다.

layers.idx가 정의하는 4개의 레이어는 변경 빈도가 낮은 것부터 높은 순서입니다.

왜 레이어가 Docker 캐싱에 중요한가

Docker 이미지는 레이어 단위로 캐싱됩니다. 만약 jar 전체를 한 덩어리로 이미지에 복사하면, 한 줄만 고쳐도 수백 MB짜리 의존성까지 통째로 새 레이어가 됩니다. 매 배포마다 이미지 push/pull이 무거워지죠.

layered jar를 이용하면 변경 빈도가 다른 콘텐츠를 별도의 Docker 레이어로 분리할 수 있습니다.

결과적으로 자주 바뀌는 우리 코드 레이어만 새로 만들어지고, 무거운 의존성 레이어는 캐시에서 재사용됩니다. 이 구조를 실제 Dockerfile에서 활용하는 방법은 다음 문서에서 다룹니다.

레이어를 직접 추출해 볼 수도 있습니다.

# jar에 어떤 레이어가 있는지 나열
java -Djarmode=tools -jar build/libs/book-api-0.0.1-SNAPSHOT.jar list-layers

# 레이어별로 디렉터리에 추출
java -Djarmode=tools -jar build/libs/book-api-0.0.1-SNAPSHOT.jar extract --layers --destination extracted

Spring Boot 3.3+부터 레이어 추출 도구가 -Djarmode=layertools에서 -Djarmode=tools 로 통합되었고, Spring Boot 4.1에서 옛 layertools 모드는 완전히 제거되었습니다. 인터넷 예제나 옛 Dockerfile에 layertools가 보이면 tools로 바꿔야 합니다.

같은 jar로 더 빨리 뜨기 — CDS와 AOT 캐시

방금 본 extract는 Docker 레이어를 나누는 용도만이 아닙니다. 애플리케이션을 푼 형태(extracted)로 실행하면 시작 시간을 크게 줄일 수 있는 길이 열립니다.

JVM은 매번 뜰 때마다 수천 개의 클래스를 읽고 · 검증하고 · 링크합니다. Spring 애플리케이션은 이 클래스가 특히 많죠. 그런데 이 작업의 결과는 매번 똑같습니다. 그렇다면 한 번 해 두고 파일로 저장했다가 다음 실행부터 재사용하면 되지 않을까 — 이것이 CDS(Class Data Sharing)와 그 후계인 AOT 캐시의 발상입니다.

CDS AOT 캐시
필요한 JDK 17+ (본 가이드의 JDK 21에서 사용 가능) 25+ (JDK 24의 JEP 483에서 도입, 25에서 확장)
저장하는 것 로딩·파싱이 끝난 클래스 이미지 클래스 + 링크·프로파일 정보까지
Spring Boot 지원 3.3+ 4.0+
플래그 -XX:ArchiveClassesAtExit → -XX:SharedArchiveFile -XX:AOTCacheOutput → -XX:AOTCache

둘 중 쓸 수 있으면 AOT 캐시가 낫습니다. 다만 JDK 25 이상이 필요합니다. 본 가이드의 기준은 JDK 21이므로 아래 예제는 CDS를 기본으로 두고, AOT 캐시 명령을 나란히 적어 둡니다. 명령의 모양은 똑같고 플래그 이름만 다릅니다.

훈련 실행(training run)

두 방식 모두 "한 번 띄웠다 끄면서 결과물을 받아 적는" 훈련 실행이 필요합니다. 여기서 Spring Boot가 제공하는 열쇠가 spring.context.exit=onRefresh 입니다 — ApplicationContext 초기화가 끝나는 순간 JVM을 종료시켜, 웹 서버를 띄우거나 요청을 받지 않고도 "실제로 로드되는 클래스 전부"를 확보합니다.

# 1) 실행 가능 jar를 푼 형태로 추출
java -Djarmode=tools -jar build/libs/book-api-0.0.1-SNAPSHOT.jar \
     extract --destination application
cd application

# 2) 훈련 실행 — 컨텍스트가 뜨자마자 종료하며 아카이브를 남긴다
#    [CDS · JDK 17+]
java -XX:ArchiveClassesAtExit=application.jsa \
     -Dspring.context.exit=onRefresh -jar book-api-0.0.1-SNAPSHOT.jar
#    [AOT 캐시 · JDK 25+]
java -XX:AOTCacheOutput=app.aot \
     -Dspring.context.exit=onRefresh -jar book-api-0.0.1-SNAPSHOT.jar

# 3) 캐시를 사용해 기동
java -XX:SharedArchiveFile=application.jsa -jar book-api-0.0.1-SNAPSHOT.jar   # CDS
java -XX:AOTCache=app.aot -jar book-api-0.0.1-SNAPSHOT.jar                    # AOT 캐시

훈련 실행은 애플리케이션을 실제로 초기화합니다. 운영 DB나 외부 API에 연결되는 설정으로 훈련하면 빌드 중에 운영 시스템을 건드리게 됩니다. 훈련 전용 프로파일(Phase 4-3)로 인메모리 DB·모의 엔드포인트를 쓰게 하세요. 그리고 캐시 파일은 애플리케이션과 JDK 버전에 묶여 있으므로, 배포마다 새로 만들어야 합니다.

Spring AOT와 함께 쓰기

여기까지가 JVM 레벨의 최적화라면, Spring AOT(processAot)는 프레임워크 레벨에서 빈 정의·프록시·설정 분석 결과를 빌드 시점에 코드로 생성해 둡니다. 둘은 겹치지 않고 곱해집니다.

# Spring AOT 처리까지 켠 상태로 기동 (AOT로 빌드한 jar에서만 의미가 있다)
java -Dspring.aot.enabled=true -XX:SharedArchiveFile=application.jsa \
     -jar book-api-0.0.1-SNAPSHOT.jar

Spring 팀이 공개한 최소 Spring MVC + Tomcat 애플리케이션 기준 측정에서, CDS만으로 시작 시간 약 1.5배 단축 · 메모리 16% 감소, 여기에 Spring AOT를 더하면 약 2배 단축 · 메모리 27% 감소가 보고되었습니다. 애플리케이션마다 편차가 크므로 반드시 여러분의 앱에서 직접 재 보세요 — 빈이 많고 초기화가 무거울수록 이득이 큽니다.

Buildpacks로 자동화하기

위 3단계를 손으로 하는 대신, Buildpacks에 맡길 수 있습니다. 환경 변수 하나면 빌드팩이 훈련 실행까지 대신해 줍니다.

// build.gradle.kts
tasks.named<org.springframework.boot.gradle.tasks.bundling.BootBuildImage>("bootBuildImage") {
    environment.set(
        mapOf(
            // CDS (JDK 17+)
            "BP_JVM_CDS_ENABLED" to "true",
            // 또는 AOT 캐시 (JDK 25+)
            // "BP_JVM_AOTCACHE_ENABLED" to "true",
        )
    )
}

네이티브 이미지와 무엇이 다른가? GraalVM 네이티브 이미지는 밀리초 단위 기동과 훨씬 적은 메모리를 주지만, 빌드가 오래 걸리고 리플렉션에 힌트가 필요하며 JIT의 피크 성능을 포기합니다. CDS·AOT 캐시는 JVM을 그대로 두고 코드 수정 없이 시작 시간을 깎는 방법입니다. Cloud Run처럼 콜드 스타트가 중요한 환경(Phase 7-1)에서 가장 먼저 시도해 볼 카드입니다.

bootRun vs bootJar

개발 중에는 jar를 만들지 않고 Gradle에서 바로 실행하는 것이 편합니다.

태스크 용도 특징
./gradlew bootRun 로컬 개발 빌드 후 곧바로 실행, 소스 클래스 디렉터리에서 구동, jar 생성 안 함
./gradlew bootJar 배포 산출물 생성 build/libs/에 실행 가능 jar 생성, 실행은 별도

bootRun에 인자나 프로파일을 넘길 때는 --args를 사용합니다.

./gradlew bootRun --args='--spring.profiles.active=local --server.port=9090'

실행 시 설정 주입: 인자 · 프로파일 · JVM 옵션

같은 jar를 환경마다 다르게 동작시키는 핵심은 실행 시점 설정 주입입니다. Spring Boot는 여러 소스에서 설정을 읽으며, 우선순위가 높은 순서대로 정리하면 다음과 같습니다.

커맨드라인 인자 (--key=value)
  > OS 환경변수 (SPRING_PROFILES_ACTIVE 등)
    > application-{profile}.yml
      > application.yml

프로파일 활성화

Phase 3에서 도입한 prod 프로파일을 켜는 방법은 세 가지입니다.

# 1) 커맨드라인 인자
java -jar app.jar --spring.profiles.active=prod

# 2) 환경변수 (컨테이너 배포에서 가장 흔함)
SPRING_PROFILES_ACTIVE=prod java -jar app.jar

# 3) JVM 시스템 프로퍼티
java -Dspring.profiles.active=prod -jar app.jar

임의의 설정 값 덮어쓰기

application.yml의 어떤 값이든 커맨드라인 인자나 환경변수로 덮어쓸 수 있습니다. 점(.) 표기를 환경변수로 쓸 때는 대문자 + 언더스코어로 변환합니다(relaxed binding).

# 커맨드라인 인자
java -jar app.jar --server.port=8081 --spring.datasource.url=jdbc:postgresql://db:5432/bookdb

# 동일한 의미의 환경변수
SERVER_PORT=8081 \
SPRING_DATASOURCE_URL=jdbc:postgresql://db:5432/bookdb \
java -jar app.jar

JVM 옵션 (JAVA_OPTS)

힙 크기, GC, 시스템 프로퍼티 같은 JVM 수준 옵션은 java 명령 앞에 둡니다. 컨테이너에서는 관례적으로 JAVA_OPTS 환경변수에 모아 둡니다.

# 힙 최대 512MB, 컨테이너 메모리 인식 활성화
java -Xmx512m -XX:+UseContainerSupport -jar app.jar

# JAVA_OPTS 패턴 (쉘에서 펼쳐서 전달)
export JAVA_OPTS="-Xmx512m -XX:MaxRAMPercentage=75.0"
java $JAVA_OPTS -jar app.jar --spring.profiles.active=prod

컨테이너 환경에서는 고정 -Xmx보다 -XX:MaxRAMPercentage 로 컨테이너에 할당된 메모리의 비율을 지정하는 편이 안전합니다. JDK 21은 cgroup 메모리 한도를 자동 인식합니다.
