부록 E. 서비스 규모·도메인별 설계 전략

Phase 0부터 7까지는 "어떻게 만드는가" 를 다뤘습니다. 컨트롤러를 만들고, 엔티티를 매핑하고, 예외를 처리하고, 배포했죠. 그 과정에서 이 가이드는 계속 하나의 정답을 제시했습니다. 입문자에게는 그게 맞습니다. 선택지를 늘리는 것보다 하나를 끝까지 해 보는 편이 훨씬 빨리 배웁니다.

하지만 실무에 나가면 사정이 달라집니다. "컨트롤러 → 서비스 → 리포지토리로 나누는 게 맞나요?" 라는 질문의 답은 서비스 규모와 도메인 성격에 따라 달라집니다. 3명이 쓰는 사내 관리 도구와, 초당 수천 건을 처리하는 주문 시스템에 같은 설계를 쓰는 것이 오히려 이상합니다.

이 부록은 두 개의 축으로 그 답을 정리합니다.

1. 이 부록이 반복해서 말하는 것

먼저 결론부터 말하겠습니다. 네 페이지를 다 읽어도 남는 문장은 하나입니다.

지금 필요한 것만 하고, 나중에 바꿀 수 있게 열어 두세요. 대부분의 설계 실패는 "너무 단순하게 시작해서"가 아니라 "쓰지도 않을 확장성을 미리 만들어서" 일어납니다. 3명짜리 팀이 마이크로서비스로 시작하면, 얻는 것은 독립 배포가 아니라 분산된 채로 여전히 얽혀 있는 시스템입니다.

2026년 Spring 커뮤니티의 논조도 정확히 이쪽입니다. Spring I/O 2026에서 Julien Topçu와 Thomas Pierrain은 Live Coding The Hive 세션에서 "잘못 설계된 마이크로서비스는 스파게티 모놀리스보다 더 나쁜 분산 모놀리스가 되기 쉽다" 고 지적했고, Oliver Drotbohm은 Domain-centric? Why Hexagonal- and Onion-Architecture are answers to the wrong question 에서 "이 연습의 실제 목표가 무엇이고, 꼭 이렇게 복잡해야 하는가" 를 물었습니다. 유행하는 아키텍처를 따라가는 대신, 지금 겪는 문제에서 출발하라는 뜻입니다.

2. 이 부록의 구성

  1. 01. 규모 단계별 설계 — 규모를 재는 기준(팀·배포 빈도·도메인 수), 4단계(S0~S3)별로 지금 할 것과 미룰 것, 단계마다 달라지는 Spring Boot 설정.
  2. 02. 패키지 구조와 모듈러 모놀리스 — 계층 우선 vs 도메인 우선 패키지, 모듈 경계를 코드로 강제하는 Spring Modulith·ArchUnit, 헥사고날/어니언 재평가, 마이크로서비스로 쪼개는 시점.
  3. 03. 도메인 성격별 전략 — CRUD·읽기 중심·쓰기 정합성·이벤트 비동기·배치 다섯 유형별로 스프링 스택을 고르는 법과 각각의 함정.
  4. 04. 의사결정 가이드 — "지금 도입해야 하나?" 판단 흐름, 규모×도메인 매트릭스, 자주 보는 안티패턴 모음.

3. 선수 지식

  • Phase 2~3 — 컨트롤러·서비스·리포지토리 3계층과 트랜잭션. 이 부록은 그 구조를 언제 바꾸는지를 다룹니다.
  • Phase 5 — HTTP 클라이언트·관측성·API 버전 관리. 서비스를 쪼개는 순간 이 셋이 전부 필수가 됩니다.
  • 부록 A·B — N+1과 DTO 프로젝션. 읽기 중심 도메인의 첫 번째 해법입니다.

이 부록의 예제는 계속 Book API를 씁니다. 다만 규모 이야기를 하려면 도메인이 하나로는 부족하므로, 도서 API가 온라인 서점으로 자라 catalog(도서) · order(주문) · member(회원) 세 영역을 갖게 된 상황을 가정합니다. 패키지 루트는 여전히 com.example.bookapi 입니다.
