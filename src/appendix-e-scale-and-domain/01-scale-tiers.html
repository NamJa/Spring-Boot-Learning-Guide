01. 규모 단계별 설계

"규모가 커지면 어떻게 해야 하나요?"라는 질문에 답하려면, 먼저 규모를 무엇으로 재는지부터 정해야 합니다. 대부분의 사람은 트래픽(RPS·MAU)을 떠올리지만, 설계를 실제로 바꾸는 것은 트래픽이 아니라 조직입니다.

1. 규모를 재는 세 가지 눈금

트래픽이 설계를 바꿔야 할 때도 물론 있습니다. 다만 그 시점은 수평 확장(인스턴스 증설)과 캐시로 더는 감당이 안 될 때입니다. 그전까지 트래픽 문제의 답은 거의 항상 "인스턴스를 늘리고, 쿼리를 고치고, 캐시를 붙인다"입니다. 자세한 것은 03. 도메인 성격별 전략에서 다룹니다.

2. 네 단계 (S0 → S3)

S0 — 프로토타입 · MVP

가설을 검증하는 단계입니다. 이 코드는 버려질 확률이 높다는 것을 전제로 씁니다.

지금 할 것

  • 단일 Gradle 모듈, 계층 우선 패키지
  • @RestController → @Service → @Repository 3계층 그대로
  • H2 또는 Docker 한 줄짜리 PostgreSQL
  • Actuator health만 노출
  • 가장 중요한 흐름 하나에만 통합 테스트
vs

지금 하지 말 것

  • 모듈 분리, 헥사고날 포트/어댑터
  • 캐시·메시지 브로커·읽기 복제본
  • 마이크로서비스, 서비스 메시
  • 커버리지 목표, 100% 테스트
  • 커스텀 프레임워크·공통 라이브러리

S1 — 프로덕션 초기

진짜 사용자가 들어왔습니다. 질문이 "동작하는가"에서 "안 죽는가, 죽으면 아는가" 로 바뀝니다. 이 가이드의 Phase 4~6이 정확히 이 단계를 위한 내용입니다.

도입할 것 이유 가이드
전역 예외 처리 + ProblemDetail 스택 트레이스가 클라이언트로 새는 것을 막는다 Phase 4-2
프로파일 분리 · 환경변수 설정 같은 이미지를 dev/prod에 쓰기 위한 최소 조건 Phase 4-3
Actuator + 메트릭 + 구조화 로그 장애를 사용자보다 먼저 알기 위해 Phase 5-3
외부 호출 타임아웃 + 재시도 외부 지연이 우리 스레드를 잠그는 장애 전파 차단 Phase 5-1
DB 마이그레이션(Flyway) ddl-auto: update로는 운영 스키마를 되돌릴 수 없다 Phase 3-5
readiness/liveness + 그레이스풀 셧다운 배포마다 요청이 끊기지 않게 Phase 6-4
API 버전 관리 준비 클라이언트가 생긴 순간부터 응답 스펙은 계약이 된다 Phase 5-5

S1에서 가장 자주 빠뜨리는 것은 외부 호출 타임아웃입니다. 정상일 때는 아무 문제가 없다가, 외부 API가 한 번 느려지는 날 전체 서비스가 같이 멈춥니다. 톰캣 스레드가 전부 그 호출을 기다리며 묶이기 때문입니다. 코드 한 줄짜리 설정이 전면 장애와 부분 실패를 가르는 지점입니다.

S2 — 성장기

팀이 늘고 도메인이 여러 개가 되었습니다. 이제 문제는 성능이 아니라 사람 사이의 간섭입니다.

S2의 정답은 대부분 서비스를 쪼개는 것이 아니라 모듈을 나누는 것입니다. 같은 배포 단위 안에서 코드의 경계만 명확히 하는 것이죠. 방법은 다음 문서에서 자세히 다룹니다.

S3 — 대규모

조직이 여러 개고, 각 조직이 독립적으로 배포하고 독립적으로 장애를 감당해야 하는 단계입니다. 여기서 비로소 서비스 분리가 값을 합니다.

서비스를 쪼개면 얻는 것과 잃는 것이 동시에 생깁니다. 얻는 것은 독립 배포·독립 확장·장애 격리입니다. 잃는 것은 로컬 트랜잭션입니다. @Transactional 한 줄로 끝나던 정합성이 사가(saga)·아웃박스·보상 트랜잭션이 됩니다. 이 비용을 감당할 준비가 되지 않았다면, 아직 S2에 머무는 편이 낫습니다.

3. 단계별로 달라지는 Spring Boot 설정

같은 Book API라도 단계마다 application.yml이 이렇게 달라집니다.

spring:
  application:
    name: book-api
  datasource:
    url: jdbc:h2:mem:bookdb
  jpa:
    hibernate:
      ddl-auto: create-drop     # 스키마는 매번 새로 — 아직 지킬 데이터가 없다
    show-sql: true

management:
  endpoints:
    web:
      exposure:
        include: health         # 이것만으로 충분
spring:
  application:
    name: book-api
  datasource:
    url: ${DB_URL}
    username: ${DB_USER}
    password: ${DB_PASSWORD}
    hikari:
      maximum-pool-size: 10     # DB max_connections / 인스턴스 수 를 넘지 않게
  jpa:
    hibernate:
      ddl-auto: validate        # 스키마 변경은 Flyway가 담당
    open-in-view: false         # 뷰 렌더링까지 커넥션을 붙잡지 않는다
  flyway:
    enabled: true
  http:
    clients:
      connect-timeout: 2s       # 외부 호출은 반드시 타임아웃
      read-timeout: 5s

server:
  shutdown: graceful

management:
  endpoints:
    web:
      exposure:
        include: health,info,metrics,prometheus
  endpoint:
    health:
      probes:
        enabled: true           # /readiness · /liveness
# S1 설정에 더해서 —
spring:
  cache:
    type: redis                 # 읽기 중심 조회를 캐시로 흡수
  data:
    redis:
      url: ${REDIS_URL}
  jpa:
    properties:
      hibernate:
        jdbc:
          batch_size: 50        # 대량 쓰기 배치

management:
  tracing:
    sampling:
      probability: 0.1          # 분산 추적 — 모듈 간 호출 경로 추적
  otlp:
    tracing:
      endpoint: ${OTLP_ENDPOINT}

open-in-view: false는 S1에서 가장 값싸게 얻는 개선입니다. 기본값 true는 뷰가 렌더링될 때까지 DB 커넥션을 붙잡고 있어, 트래픽이 오르면 커넥션 풀이 먼저 마릅니다. 끄면 지연 로딩이 컨트롤러에서 터지는데, 그건 버그가 드러난 것이지 새로 생긴 것이 아닙니다. (부록 A-4)

4. 단계를 건너뛰면 생기는 일

건너뛴 것 겉으로 보이는 증상 실제 원인
S0 → S3 (바로 마이크로서비스) 기능 하나 추가에 서비스 4개를 고치고 4번 배포 도메인 경계를 모르는 채로 물리적으로 먼저 쪼갬 → 분산 모놀리스
S1 생략 (관측성 없이 성장) "느리다"는 제보는 오는데 어디가 느린지 모름 메트릭·추적이 없어 추측으로 튜닝
S2 생략 (경계 없이 커짐) 신규 입사자가 3개월째 코드를 못 읽음 모든 것이 모든 것을 참조 — 변경 영향 예측 불가
과설계 (S1인데 S3 구조) 인터페이스와 어댑터가 구현체보다 많음 추상화 비용만 지불하고 교체는 한 번도 안 함

컨퍼런스 인사이트 (Spring I/O 2026). Julien Topçu·Thomas Pierrain의 Live Coding The Hive: building a microservices-ready modular monolith 세션은 이 함정을 정면으로 다룹니다. 핵심 주장은 "모듈을 느슨하게 유지한 모놀리스는 필요할 때 서비스로 꺼낼 수 있지만, 강하게 결합된 채 쪼갠 서비스는 되돌릴 수 없다" 는 것입니다. 순서가 중요합니다 — 경계를 먼저 긋고, 배포를 나중에 나눕니다.

정리

  • 규모는 트래픽이 아니라 팀 크기 · 배포 독립성 · 도메인 수로 잽니다.
  • S0는 버릴 코드를 빨리, S1은 안 죽고 보이게, S2는 서로 안 밟게, S3는 독립적으로.
  • S2의 답은 대개 서비스 분리가 아니라 모듈 분리입니다.
  • 서비스를 쪼개는 순간 @Transactional을 잃습니다. 그 비용을 감당할 수 있을 때만 쪼갭니다.
