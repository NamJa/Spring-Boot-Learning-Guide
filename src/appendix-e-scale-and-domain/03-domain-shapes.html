03. 도메인 성격별 전략

같은 규모라도 도메인의 성격이 다르면 쓰는 도구가 달라집니다. 초당 5,000건을 읽는 서비스와 초당 500건을 쓰는 서비스는 병목도, 해법도, 실패 방식도 전부 다릅니다.

이 문서는 실무에서 만나는 도메인을 다섯 가지 성격으로 나누고, 각각에 대해 "무엇이 먼저 터지고, 무엇으로 막는가"를 정리합니다. 하나의 서비스가 여러 성격을 동시에 갖는 것이 보통이므로, 모듈별로 다른 전략을 쓰는 것이 자연스럽습니다.

① CRUD 중심 — 아무것도 하지 마세요

사내 관리 도구, 백오피스, 설정 화면처럼 동시 사용자가 수십 명인 도메인입니다. 이 가이드 Phase 2~4의 구조 그대로가 정답이고, 여기에 무엇을 더하는 것은 대부분 손해입니다.

하지 말 것 이유
캐시 데이터가 자주 바뀌는데 조회는 드물다 — 캐시 무효화 버그만 얻는다
CQRS · 읽기 모델 분리 읽기 부하가 없다. 동기화 코드만 늘어난다
비동기 처리 관리자는 결과를 지금 화면에서 확인하고 싶어 한다
DTO 계층 3중 분리 엔티티 → 도메인 → 응답 3단 매핑. 필드 추가에 파일 6개를 고치게 된다

CRUD 도메인에서 유일하게 값이 확실한 투자는 입력 검증(Phase 4-1)과 감사 로그입니다. "누가 언제 이 값을 바꿨는가"는 백오피스에서 가장 자주 나오는 질문입니다. Spring Data JPA의 @CreatedDate·@LastModifiedBy 감사 기능으로 거의 공짜로 얻을 수 있습니다.

② 읽기 중심 — 순서대로 올라가세요

도서 목록·검색·상세처럼 조회가 쓰기보다 압도적으로 많은 도메인입니다. 여기서 흔한 실수는 문제를 진단하기 전에 Redis부터 붙이는 것입니다. 대부분의 조회 성능 문제는 캐시가 아니라 쿼리 문제입니다.

package com.example.bookapi.service

import org.springframework.cache.annotation.Cacheable
import org.springframework.stereotype.Service
import org.springframework.transaction.annotation.Transactional

@Service
@Transactional(readOnly = true)          // 클래스 기본값을 읽기 전용으로
class BookService(
    private val bookRepository: BookRepository,
) {

    // 자주 조회되고 거의 안 바뀌는 단건 — 캐시 대상으로 적합
    @Cacheable(cacheNames = ["books"], key = "#id")
    fun findById(id: Long): BookResponse = ...

    // 목록은 캐시하지 않는다 — 필터 조합마다 키가 폭발한다
    fun findAll(): List<BookResponse> = ...

    @Transactional                        // 쓰기 메서드만 개별로 되돌린다
    fun create(request: CreateBookRequest): BookResponse = ...
}

목록 조회를 캐시하지 마세요. 필터·정렬·페이지 조합마다 캐시 키가 생겨 히트율은 낮고 메모리만 먹습니다. 게다가 도서 한 권이 바뀌면 그 책이 포함된 모든 목록 캐시를 지워야 하는데, 그게 어느 것인지 알 방법이 없습니다. 캐시는 키가 명확한 단건 조회부터 시작합니다.

③ 쓰기·정합성 중심 — 트랜잭션 경계가 전부

주문·결제·재고처럼 틀리면 돈이 되는 도메인입니다. 여기서 성능보다 먼저 걱정할 것은 정합성입니다.

가장 흔한 사고: 재고 차감 경쟁

재고 1권을 두 사람이 동시에 주문했습니다. 두 트랜잭션이 모두 "재고 1권 남음"을 읽고, 각자 0으로 만들어 저장합니다. 2권이 팔렸는데 재고는 0이 됩니다.

package com.example.bookapi.repository

import com.example.bookapi.domain.Book
import org.springframework.data.jpa.repository.JpaRepository
import org.springframework.data.jpa.repository.Modifying
import org.springframework.data.jpa.repository.Query
import org.springframework.data.repository.query.Param

interface BookRepository : JpaRepository<Book, Long> {

    // 조건부 원자 갱신 — 재고가 충분할 때만 차감되고, 갱신된 행 수를 돌려준다
    @Modifying(clearAutomatically = true)
    @Query("update Book b set b.stock = b.stock - :qty where b.id = :id and b.stock >= :qty")
    fun decreaseStock(@Param("id") id: Long, @Param("qty") qty: Int): Int
}
@Transactional
fun decreaseStock(id: Long, quantity: Int) {
    val updated = bookRepository.decreaseStock(id, quantity)
    if (updated == 0) {
        // 0행이 갱신됐다 = 재고가 부족했다. 예외로 명확히 구분한다
        throw OutOfStockException(id)
    }
}

트랜잭션 경계에서 지킬 것

규칙 이유
트랜잭션 안에서 외부 HTTP 호출 금지 외부가 5초 느려지면 DB 커넥션을 5초 붙잡는다. 커넥션 풀이 먼저 마른다
트랜잭션은 짧게 긴 트랜잭션은 락 유지 시간을 늘려 경합을 키운다
커밋 이후 작업은 @TransactionalEventListener "주문 저장 후 알림 발송"을 같은 트랜잭션에 넣으면 알림 실패로 주문이 롤백된다
자기 호출로는 @Transactional이 안 걸린다 프록시를 거치지 않기 때문 (부록 C-3)

낙관적 락 충돌은 재시도하면 대부분 성공합니다. Spring Framework 7의 @Retryable(Phase 5-1)을 쓰면 외부 라이브러리 없이 처리할 수 있습니다. 단, 재시도는 트랜잭션 바깥에서 걸어야 합니다 — 이미 롤백된 트랜잭션 안에서 다시 시도해도 소용없습니다.

④ 이벤트·비동기 중심 — 결합을 끊는 대신 어려움을 산다

주문 완료 알림, 정산 집계, 외부 시스템 연동처럼 지금 당장 끝나지 않아도 되는 일입니다. 이벤트로 옮기면 응답이 빨라지고 모듈 결합이 끊어집니다. 대신 동기 호출에는 없던 문제들이 따라옵니다.

컨퍼런스 인사이트 (Spring I/O 2026). Victor Rentea는 Top 10 Event-Driven Architecture Pitfalls 세션을 "REST API를 부르는 대신 메시지를 보낸다 — 뭐가 잘못될 수 있겠어?" 라는 문장으로 엽니다. 150개 조직에서 실제로 목격한 함정으로 중복 전달, 순서 뒤바뀜, 경쟁 조건, dual-write, 소비자 오류, 메시지 유실, 메시지에 담긴 개인정보 등을 꼽았습니다. 요지는 명확합니다 — 이벤트는 결합을 끊어 주지만, 끊긴 자리에 새로운 실패 모드가 들어옵니다.

단일 애플리케이션 안에서 시작한다면 Spring Modulith의 이벤트가 가장 값싼 출발점입니다. spring-modulith-starter-jpa가 아웃박스를 대신 구현해 주므로, 브로커를 도입하지 않고도 유실 방지와 재발행을 얻습니다. 나중에 브로커로 옮길 때도 리스너 코드는 그대로 둘 수 있습니다.

package com.example.bookapi.service

import org.springframework.context.ApplicationEventPublisher
import org.springframework.stereotype.Service
import org.springframework.transaction.annotation.Transactional

@Service
class OrderService(
    private val events: ApplicationEventPublisher,
) {
    @Transactional
    fun placeOrder(command: PlaceOrderCommand): OrderResponse {
        val order = ...    // 저장

        // 발행 시점은 트랜잭션 안이지만, 리스너는 커밋 후에 실행된다
        events.publishEvent(OrderPlaced(order.id, command.bookId, command.quantity))
        return order.toResponse()
    }
}

⑤ 배치·대량 처리 — 메모리와 트랜잭션 길이

도서 10만 건 일괄 등록, 야간 정산 집계 같은 작업입니다. 웹 요청과 완전히 다른 규칙이 적용됩니다.

증상 원인 대응
OutOfMemoryError 영속성 컨텍스트가 10만 엔티티를 모두 들고 있다 일정 건수마다 flush() + clear(), 또는 청크 단위 처리
INSERT가 10만 번 나감 JDBC 배치가 꺼져 있다 spring.jpa.properties.hibernate.jdbc.batch_size 설정 + IDENTITY 대신 시퀀스 사용
배치 도는 동안 API가 느려짐 같은 커넥션 풀·같은 DB를 쓴다 배치 전용 데이터소스, 또는 읽기 복제본·별도 시간대로 분리
중간에 실패하면 처음부터 전체를 하나의 트랜잭션으로 묶었다 청크 단위 커밋 + 재시작 지점 기록 (Spring Batch가 이 문제를 위해 존재합니다)

@GeneratedValue(strategy = IDENTITY)를 쓰면 Hibernate의 JDBC 배치가 무력화됩니다. INSERT를 실제로 실행해야 ID를 알 수 있으므로 쓰기를 모아 둘 수 없기 때문입니다. 대량 INSERT가 있는 도메인이라면 SEQUENCE 전략을 쓰세요. (Phase 3-2)

정리 — 성격별 요약

성격 먼저 터지는 곳 첫 번째 해법 과설계 신호
① CRUD 거의 없음 검증 + 감사 로그 캐시·CQRS 도입
② 읽기 중심 쿼리 수 · 커넥션 풀 N+1 제거 → DTO 프로젝션 진단 전에 Redis
③ 쓰기·정합성 락 경합 · 트랜잭션 길이 조건부 원자 UPDATE 분산 락부터 검토
④ 이벤트·비동기 중복 · 유실 · 순서 아웃박스 + 멱등 처리 모든 호출을 이벤트로
⑤ 배치·대량 메모리 · 트랜잭션 길이 청크 커밋 + JDBC 배치 실시간 스트리밍 파이프라인
