02. 데이터 계층 운영 — 커넥션 풀·캐시·락

운영 장애 회고에서 가장 자주 등장하는 데이터 계층의 세 단어는 풀(pool) · 캐시(cache) · 락(lock)입니다. 셋 모두 "느려서 늘렸는데 더 느려졌다"는 공통 서사를 갖습니다. 이 페이지는 그 서사가 왜 반복되는지를 CS 배경(큐잉, 컨텍스트 스위칭, 경합)으로 설명하고, Spring Boot 4.1에서의 구체적인 설정과 코드로 답합니다.

1. 커넥션 풀 — 크면 느려진다

HikariCP는 Spring Boot의 기본 풀이고 기본 크기는 10입니다. 커넥션 대기가 늘면 대부분의 팀이 첫 번째로 하는 일은 maximum-pool-size를 50, 100으로 올리는 것입니다. 2026년의 수많은 글이 이것을 "거의 항상 잘못된 대응"이라고 부릅니다. 이유는 DB 쪽에 있습니다.

왜 커넥션이 많으면 느려지나 (CS)

PostgreSQL은 커넥션마다 프로세스 하나를 씁니다. 코어가 8개인 DB 서버에 커넥션 100개가 동시에 쿼리를 던지면, 실제로 실행되는 것은 8개이고 92개는 CPU 스케줄러 큐에서 기다리며 컨텍스트 스위칭·캐시 미스·락 경합만 늘립니다. HikariCP 위키의 유명한 공식이 여기서 나옵니다.

기본값을 손봐야 하는 항목

# application.yml — Boot 4.1.1 기준
spring:
  datasource:
    connection-fetch: lazy              # 4.1 신설: 첫 SQL 실행 시점에 커넥션 획득 (LazyConnectionDataSourceProxy)
    hikari:
      maximum-pool-size: 10             # 공식대로. 늘리기 전에 §1 흐름도를 따르세요
      minimum-idle: 10                  # = maximum. 유휴 축소/재생성 비용을 없앤다 (HikariCP 권장)
      connection-timeout: 3000          # 기본 30s → 3s. 빨리 실패해야 스레드가 쌓이지 않는다
      max-lifetime: 1800000             # 30분. DB·LB·클라우드 NAT의 유휴 끊김 시간보다 반드시 짧게
      keepalive-time: 300000            # 5분마다 유휴 커넥션 검사 — NAT가 조용히 끊는 커넥션 대비
      leak-detection-threshold: 10000   # 10초 이상 반환 안 된 커넥션을 로그로 — 개발·스테이징에서 켠다

connection-fetch: lazy가 왜 중요한가. @Transactional 메서드가 시작되면 원래는 즉시 커넥션을 빌립니다. 메서드 첫 줄이 외부 API 호출이면 그 2초 동안 커넥션은 아무 일도 안 하면서 풀에서 빠져 있습니다. lazy 모드는 첫 SQL이 실행될 때 빌리므로 커넥션 점유 시간 = 실제 DB 작업 시간에 가까워집니다. 읽기 전용 트랜잭션에서 커넥션을 아예 안 쓰는 경로(캐시 히트)도 커넥션을 빌리지 않습니다.

"대기가 늘었다"에 대응하는 순서

Micrometer가 HikariCP 메트릭을 자동 노출하므로(Phase 5-3) 알람은 세 개면 충분합니다: hikaricp.connections.pending(대기 > 0 지속), hikaricp.connections.timeout(증가율), hikaricp.connections.usage(p99 사용 시간).

2. 캐시 — 계층과 무효화

캐시는 부록 E ②(읽기 중심)에서 "쿼리 최적화 다음"으로 도입하는 도구입니다. 여기서는 도입하기로 결정한 뒤의 문제 — 계층을 어떻게 나누고, 만료 순간에 무엇이 터지는가를 다룹니다.

// build.gradle.kts
implementation("org.springframework.boot:spring-boot-starter-cache")
implementation("com.github.ben-manes.caffeine:caffeine")            // L1 — Boot BOM이 버전 관리
// L2가 필요해지면: implementation("org.springframework.boot:spring-boot-starter-data-redis")
spring:
  cache:
    type: caffeine
    cache-names: books
    caffeine:
      # 만료를 한 시점에 몰지 않도록 expireAfterWrite는 §2.1 스탬피드 절의 지터와 함께 설계
      spec: maximumSize=10000,expireAfterWrite=10m,recordStats
package com.example.bookapi.service

import org.springframework.cache.annotation.CacheEvict
import org.springframework.cache.annotation.Cacheable
import org.springframework.stereotype.Service
import org.springframework.transaction.annotation.Transactional

@Service
@Transactional(readOnly = true)
class BookService(private val bookRepository: BookRepository) {

    // sync = true: 같은 키의 동시 요청 중 하나만 DB로 가고 나머지는 그 결과를 기다린다 (single-flight)
    @Cacheable(cacheNames = ["books"], key = "#id", sync = true)
    fun getBook(id: Long): BookResponse =
        bookRepository.findById(id).orElseThrow { BookNotFoundException(id) }.toResponse()

    // 쓰기 경로에서 즉시 무효화 — TTL은 "안전망"이지 무효화 전략이 아니다
    @Transactional
    @CacheEvict(cacheNames = ["books"], key = "#id")
    fun updateBook(id: Long, request: UpdateBookRequest): BookResponse { /* … */ }
}

2.1 캐시 스탬피드(cache stampede) — 만료 순간의 폭주

인기 도서 캐시가 10분에 만료되는 순간, 그 키를 읽던 2,000개 요청이 동시에 캐시 미스를 내고 같은 쿼리 2,000개가 DB로 갑니다(thundering herd). 가상 스레드 환경에서는 이 2,000개가 큐에 걸리지 않고 정말 동시에 갑니다. 방어는 네 겹이고, 싼 것부터 씁니다.

순서기법Spring에서막는 것
1요청 병합(single-flight)@Cacheable(sync = true) — 위 코드한 인스턴스 안의 동일 키 중복 조회. 이것만으로 대부분 해결
2TTL 지터키마다 만료를 ±10% 흩뜨림 — Caffeine.expireAfter(Expiry)로 직접, 또는 Redis SET … PX (ttl + random)여러 키가 같은 순간에 만료되는 것(배포 직후 워밍업 후 10분 뒤 일제 만료)
3조기 재계산(stale-while-revalidate)Caffeine refreshAfterWrite=8m + expireAfterWrite=10m — 만료 전에 백그라운드로 갱신만료 순간 자체 — 사용자는 항상 캐시된 값을 받는다
4분산 락§3의 RedisLockRegistry — 여러 인스턴스 중 하나만 재계산인스턴스 N개가 각각 1번씩 DB를 치는 것. 비용이 큰 결과에만

refreshAfterWrite는 @Cacheable의 기본 경로로는 동작하지 않습니다. Spring Cache 추상화가 CacheLoader를 넘기지 않기 때문에, 이 기능이 필요하면 CaffeineCacheManager.setCacheLoader(...)로 로더를 직접 등록해야 합니다. 그 전까지는 1 + 2로 충분한지 먼저 측정하세요(cache.gets{result=miss} 메트릭).

2.2 무효화 원칙 세 줄

  • 쓰기 경로에서 즉시 evict한다. TTL은 evict를 놓친 경우의 안전망이다.
  • L1이 여러 인스턴스에 있으면 한 인스턴스의 evict가 다른 인스턴스에 전파되지 않는다. Redis Pub/Sub으로 "이 키 지워" 메시지를 보내거나(Boot 4.1의 @RedisListener가 이 수신 코드를 단순화), L1 TTL을 짧게(30초~1분) 잡아 불일치 창을 좁힌다.
  • 캐시 키에 버전을 넣는다(books:v2:42). 응답 DTO 구조가 바뀌는 배포에서 옛 캐시가 역직렬화 오류를 내는 사고를 막는다.

3. 락 — 낙관적 → DB → 분산, 이 순서로

"주문 두 건이 동시에 마지막 재고 1개를 차감했다" 같은 문제를 만나면 곧바로 Redis 분산 락을 떠올리기 쉽습니다. 하지만 락은 비용이 가장 큰 도구이고, 대부분의 경합은 그 앞 단계에서 해결됩니다.

3.1 Redis 분산 락의 원리와 함정 (CS)

원리는 한 명령입니다. SET lock:stock:42 <token> NX PX 30000 — 키가 없을 때만(NX) 만들고 30초 후 자동 삭제(PX). Redis가 단일 스레드로 명령을 처리하므로 이 한 줄이 원자적입니다. 함정은 전부 TTL에 있습니다.

  • TTL은 데드락 방지 장치이자 정합성 구멍입니다. 작업이 30초를 넘기면 락이 풀리고 두 인스턴스가 동시에 임계 구역에 들어갑니다. GC 멈춤, 네트워크 지연이 이것을 실제로 일으킵니다.
  • 해제는 내 토큰일 때만. 그냥 DEL하면 TTL 만료 후 남이 잡은 락을 내가 지웁니다. 토큰 비교 + 삭제를 Lua 스크립트로 원자화해야 합니다.
  • Martin Kleppmann의 Redlock 비판(2016)은 여전히 유효합니다: Redis 락은 효율성 도구(같은 일을 두 번 안 하기)로 쓰고, 정확성 보장(두 번 하면 돈이 잘못 나감)은 DB 제약·멱등성(03)에 맡깁니다.

Spring에서는 이 세부를 직접 구현하지 않습니다. Spring Integration의 RedisLockRegistry가 토큰·Lua 해제·TTL 갱신을 처리합니다.

// build.gradle.kts
implementation("org.springframework.boot:spring-boot-starter-data-redis")
implementation("org.springframework.integration:spring-integration-redis")   // Boot BOM 관리
package com.example.bookapi.config

import org.springframework.context.annotation.Bean
import org.springframework.context.annotation.Configuration
import org.springframework.data.redis.connection.RedisConnectionFactory
import org.springframework.integration.redis.util.RedisLockRegistry

@Configuration(proxyBeanMethods = false)
class LockConfig {
    @Bean
    fun lockRegistry(cf: RedisConnectionFactory) =
        RedisLockRegistry(cf, "bookapi-locks", 30_000)   // 키 접두어, TTL 30초
}
package com.example.bookapi.service

import org.springframework.integration.support.locks.LockRegistry
import org.springframework.stereotype.Service
import java.util.concurrent.TimeUnit

@Service
class CatalogSyncService(
    private val lockRegistry: LockRegistry,
    private val publisherClient: PublisherClient,
) {
    // 여러 인스턴스가 같은 @Scheduled를 돌려도 출판사 API 동기화는 한 인스턴스만 수행
    fun syncCatalog() {
        val lock = lockRegistry.obtain("catalog-sync")
        if (!lock.tryLock(1, TimeUnit.SECONDS)) return      // 남이 하고 있으면 조용히 물러난다
        try {
            publisherClient.fetchUpdatedSince(lastSyncedAt()).forEach(::upsert)
        } finally {
            lock.unlock()                                    // 내 토큰일 때만 해제 — 레지스트리가 보장
        }
    }
}

이 예제가 재고 차감이 아니라 카탈로그 동기화인 데 주목하세요. 재고는 DB 행이므로 @Version이나 FOR UPDATE가 정답이고, 외부 API 호출을 "인스턴스 중 하나만"으로 제한하는 것이 분산 락의 제자리입니다.

4. 체크리스트 — 규모 단계별

단계(부록 E)커넥션 풀캐시락
S0 1팀·1인스턴스기본 10 + connection-timeout 3s + connection-fetch: lazy없음 (측정 먼저)DB 제약 + @Version
S1 인스턴스 2~3합계 ≤ DB max_connections 확인, pending 알람L1 Caffeine + sync=true경합 잦은 행만 PESSIMISTIC_WRITE
S2 여러 팀·자동 확장외부 풀러(PgBouncer / Cloud SQL 커넥터) 검토L2 Redis + 키 버전 + Pub/Sub 무효화스케줄·외부 연동에 RedisLockRegistry
S3 서비스 분리서비스별 DB → 공식을 서비스별로 다시 계산서비스별 캐시 소유권 명확화분산 트랜잭션 대신 아웃박스·멱등성
