01. 가상 스레드 실전 — 스레드 모델부터 병목의 이동까지

Phase 0-5에서 우리는 spring.threads.virtual.enabled=true 한 줄로 가상 스레드를 켰습니다. 2026년 현재 새 Spring Boot 서비스는 이 설정을 기본으로 켜고 시작하는 것이 보편이 됐고, "I/O 위주 작업에 리액티브가 기본"이던 시대는 빠르게 지나가고 있습니다. 그런데 같은 해 Medium과 Reddit에 가장 많이 올라온 후기의 제목은 이렇습니다. "가상 스레드를 켰더니 테스트에선 빨라졌는데, 운영에서 터졌다."

이 페이지는 그 후기들이 공통으로 짚는 세 가지 함정(피닝 · ThreadLocal 팽창 · 병목의 이동)을 CS 배경부터 설명하고, Kotlin 개발자에게 특히 중요한 코루틴과의 관계를 정리합니다.

1. CS 복습 — 스레드 하나의 값은 얼마인가

플랫폼(OS) 스레드는 커널이 스케줄링하는 자원입니다. 만들 때 스택 메모리를 예약하고(JVM 기본 약 1MB), 블로킹 I/O를 만나면 커널이 컨텍스트 스위칭으로 다른 스레드를 올립니다. 이 스위칭은 마이크로초 단위지만 캐시를 비우고, 스레드 수가 수천을 넘으면 스케줄러 자체가 부담이 됩니다. 그래서 Tomcat은 요청 스레드를 기본 200개로 제한합니다. 즉 전통적인 MVC 서버는 "동시에 블로킹 중인 요청 200개"가 상한이었습니다.

"마운트/언마운트"는 JVM이 가상 스레드의 스택 프레임을 힙에 복사해 두고 캐리어 스레드를 놓아 주는 동작입니다. JDK의 블로킹 API(Socket, Thread.sleep, ReentrantLock, JDBC 드라이버의 소켓 읽기 등)는 이 지점에서 협력하도록 다시 구현됐습니다. 그래서 코드를 바꾸지 않아도 동작합니다 — 협력하지 못하는 경우가 바로 다음 절의 피닝입니다.

2. 한 줄의 파급 — Spring Boot가 바꾸는 것

spring.threads.virtual.enabled=true는 요청 스레드만 바꾸는 것이 아닙니다. Spring Boot는 이 플래그 하나로 블로킹이 일어나는 모든 실행기를 가상 스레드로 교체합니다.

3. 함정 ① 피닝(pinning) — 내려오지 못하는 가상 스레드

피닝은 가상 스레드가 블로킹 중인데도 캐리어 스레드를 놓지 못하는 상황입니다. 캐리어가 코어 수만큼(예: 4개)밖에 없으므로, 피닝된 가상 스레드 4개가 동시에 I/O를 기다리면 서버 전체가 멈춘 것처럼 보입니다. 이것이 "테스트에선 괜찮았는데 운영에서 멈췄다"의 가장 흔한 원인입니다.

피닝 원인JDK 21 ~ 23JDK 24+ (JEP 491)Kotlin에서 주의할 곳
synchronized 블록/메서드 안에서 블로킹 I/O 피닝됨 해결 — 모니터 대기 중에도 언마운트 synchronized(lock) { }, @Synchronized는 JVM 모니터 그대로 → JDK 21이면 피닝
네이티브 메서드(JNI) 프레임 위에서 블로킹 피닝됨 여전히 피닝됨 네이티브 드라이버·압축 라이브러리 호출 중 I/O
클래스 초기화(static init) 중 블로킹 피닝됨 여전히 피닝됨(드묾) object 초기화 블록에서 원격 호출 금지

본 가이드의 기준(JDK 21)에서는 synchronized를 ReentrantLock으로 바꾸는 것이 가장 확실한 해법입니다. Book API에서 외부 평점 API 응답을 잠깐 캐싱하는 클라이언트를 예로 들면:

package com.example.bookapi.client

import org.springframework.stereotype.Component
import java.time.Duration
import java.time.Instant
import java.util.concurrent.locks.ReentrantLock
import kotlin.concurrent.withLock

@Component
class RatingCache(private val ratingClient: RatingClient) {

    private val lock = ReentrantLock()          // ❌ synchronized / @Synchronized → JDK 21에선 피닝
    private var cached: Map<Long, Double> = emptyMap()
    private var loadedAt: Instant = Instant.EPOCH

    fun ratingOf(bookId: Long): Double? = lock.withLock {   // ✅ ReentrantLock은 대기 중 캐리어를 놓아 준다
        if (Duration.between(loadedAt, Instant.now()) > Duration.ofMinutes(5)) {
            cached = ratingClient.fetchAll()    // 블로킹 HTTP 호출 — 락 안에서 I/O
            loadedAt = Instant.now()
        }
        cached[bookId]
    }
}

진단 도구를 먼저 켜세요. JFR 이벤트 jdk.VirtualThreadPinned(JDK 21+, 기본 20ms 이상 피닝만 기록)가 표준입니다. 시스템 속성 -Djdk.tracePinnedThreads=full은 JDK 23까지만 동작하고 JDK 24에서 제거됐습니다. 운영에서는 JFR을 켜 두고(-XX:StartFlightRecording), 피닝 이벤트가 잡히면 스택에서 synchronized나 네이티브 프레임을 찾습니다.

4. 함정 ② ThreadLocal 팽창 — 그리고 JDK 25 Scoped Values

ThreadLocal은 가상 스레드에서도 정상 동작합니다. 문제는 규모입니다. 스레드 200개일 때 무해했던 "스레드당 캐시"(포매터, 버퍼, 직렬화 컨텍스트)가 가상 스레드 수십만 개에서는 각각 복사되어 힙을 채웁니다. 특히 InheritableThreadLocal은 자식 스레드마다 값을 복사하므로 팬아웃이 많은 코드에서 눈에 띄게 늘어납니다.

JDK 25는 이 문제의 정식 대안으로 Scoped Values(JEP 506, final)를 넣었습니다. 값이 불변이고, 범위(scope)가 끝나면 자동으로 사라지며, 자식 스레드에 복사 없이 공유됩니다. "현재 요청의 회원 ID를 서비스 깊숙이까지 전달"하는 용도에 정확히 맞습니다.

// JDK 25+ (JDK 21에서는 preview 기능 — 운영 코드에는 권장하지 않음)
package com.example.bookapi.config

import java.lang.ScopedValue

object RequestScope {
    val MEMBER_ID: ScopedValue<Long> = ScopedValue.newInstance()
}

// 필터/인터셉터에서 바인딩 — 이 블록 안에서만 유효, 끝나면 자동 해제
ScopedValue.where(RequestScope.MEMBER_ID, memberId).run {
    chain.doFilter(request, response)
}

// 서비스 어디서든 읽기 — 바인딩되지 않았으면 NoSuchElementException
val current = RequestScope.MEMBER_ID.get()

Spring의 RequestContextHolder, SecurityContextHolder, SLF4J MDC는 여전히 ThreadLocal 기반이고 그대로 잘 동작합니다. 여러분이 직접 만든 ThreadLocal, 특히 큰 객체를 담는 것만 점검하세요. 힙 덤프에서 ThreadLocalMap이 상위에 보이면 그것이 신호입니다.

5. 함정 ③ 병목이 이동한다 — 스레드 풀이 사실 백프레셔였다

이것이 2026년 후기의 핵심 통찰입니다. Tomcat의 200개 상한은 제약이었지만 동시에 보호막이었습니다. 동시 요청이 200개를 넘으면 큐에서 기다렸고, 그 덕에 DB에는 동시 쿼리가 200개를 넘지 않았습니다. 가상 스레드는 이 보호막을 걷어 냅니다. 이제 트래픽 급증 시 20,000개의 요청이 동시에 HikariCP(기본 10개)에 커넥션을 요구하고, 30초 후 SQLTransientConnectionException이 폭발합니다.

Spring Framework 7은 정확히 이 용도로 @ConcurrencyLimit을 넣었습니다. 공식 문서도 "가상 스레드에서는 스레드 풀 상한이 없으므로 특히 유용하다"고 설명합니다. 출판사 API로 도서를 일괄 가져오는 서비스 메서드에 상한을 두면:

package com.example.bookapi.service

import org.springframework.resilience.annotation.ConcurrencyLimit
import org.springframework.stereotype.Service

@Service
class BookImportService(private val publisherClient: PublisherClient) {

    // 가상 스레드 20,000개가 몰려도 이 메서드는 동시에 20개만 실행 — 나머지는 대기(BLOCK)
    @ConcurrencyLimit(20)
    fun importFromPublisher(isbn: String): BookImportResult =
        publisherClient.fetch(isbn).toImportResult()
}
// 애너테이션 처리 활성화 (Phase 5-1 §7의 @Retryable과 같은 스위치)
package com.example.bookapi.config

import org.springframework.context.annotation.Configuration
import org.springframework.resilience.annotation.EnableResilientMethods

@Configuration(proxyBeanMethods = false)
@EnableResilientMethods
class ResilienceConfig

DB 쪽은 Boot 4.1의 지연 커넥션이 압력을 줄입니다. spring.datasource.connection-fetch=lazy를 켜면 LazyConnectionDataSourceProxy가 트랜잭션 시작 시점이 아니라 첫 SQL 실행 시점에 커넥션을 빌립니다. 트랜잭션 안에서 외부 API를 먼저 호출하는 코드가 있다면 커넥션 점유 시간이 크게 줄어듭니다(자세한 설정은 02).

6. 구조적 동시성 — JDK의 답과 Kotlin의 답

가상 스레드가 "스레드를 싸게" 만들었다면, 다음 질문은 "수천 개의 스레드를 어떻게 묶어 관리하나"입니다. 하나가 실패하면 나머지를 취소하고, 부모가 끝나기 전에 자식이 모두 끝나야 하는 규칙 — 이것이 구조적 동시성입니다. JDK는 StructuredTaskScope(JEP 505)로 답하지만 JDK 25에서도 아직 preview입니다. Kotlin 코루틴은 이것을 2018년부터 정식으로 갖고 있었습니다(coroutineScope, 자동 취소 전파).

관점가상 스레드 (+ StructuredTaskScope)Kotlin 코루틴
코드 변경없음 — 기존 블로킹 코드 그대로suspend 전파, 라이브러리도 suspend 버전 필요
취소·타임아웃StructuredTaskScope는 JDK 25 preview. 정식 아님정식 — withTimeout, 부모 취소 시 자식 자동 취소
디버깅일반 스레드 스택 — IDE·프로파일러가 그대로 이해코루틴 디버거 필요, 스택이 끊겨 보일 수 있음
Spring MVC 통합설정 한 줄컨트롤러 suspend fun 지원(WebFlux에서 더 자연스러움)
성능벤치마크상 코루틴이 구조적 팬아웃에서 4~8% 앞서지만, 서버 애플리케이션에서는 의미 없는 차이. 병목은 어차피 I/O 상대편

Book API의 도서 상세 조회가 재고와 평점을 병렬로 가져와야 한다면, MVC + 가상 스레드 환경에서 두 가지 방식이 모두 가능합니다.

package com.example.bookapi.service

import org.springframework.stereotype.Service
import java.util.concurrent.Executors

@Service
class BookDetailService(
    private val bookService: BookService,
    private val inventoryClient: InventoryClient,
    private val ratingCache: RatingCache,
) {
    fun detail(id: Long): BookDetailResponse {
        val book = bookService.getBook(id)
        // 태스크마다 가상 스레드 하나 — 풀 크기 고민 없음. use{}가 스코프 종료를 보장
        Executors.newVirtualThreadPerTaskExecutor().use { exec ->
            val stock  = exec.submit<Int>     { inventoryClient.stockOf(id) }
            val rating = exec.submit<Double?> { ratingCache.ratingOf(id) }
            return BookDetailResponse.of(book, stock.get(), rating.get())
        }
    }
}

단순하지만 하나가 실패해도 다른 하나가 취소되지 않습니다. 취소가 중요하면 코루틴 탭을 보세요.

package com.example.bookapi.service

import kotlinx.coroutines.Dispatchers
import kotlinx.coroutines.async
import kotlinx.coroutines.coroutineScope
import kotlinx.coroutines.runBlocking
import kotlinx.coroutines.withContext
import kotlinx.coroutines.withTimeout
import org.springframework.stereotype.Service

@Service
class BookDetailService(
    private val bookService: BookService,
    private val inventoryClient: InventoryClient,
    private val ratingCache: RatingCache,
) {
    // MVC 컨트롤러가 일반 fun을 부르므로 경계에서 runBlocking — 가상 스레드 위라서 캐리어를 막지 않음
    fun detail(id: Long): BookDetailResponse = runBlocking {
        val book = bookService.getBook(id)
        withTimeout(800) {                          // 800ms 넘으면 둘 다 취소
            coroutineScope {                        // 하나가 실패하면 나머지도 취소
                val stock  = async(Dispatchers.IO) { inventoryClient.stockOf(id) }
                val rating = async(Dispatchers.IO) { ratingCache.ratingOf(id) }
                BookDetailResponse.of(book, stock.await(), rating.await())
            }
        }
    }
}

kotlinx-coroutines-core 의존성이 필요합니다(Boot BOM이 버전을 관리). Dispatchers.IO의 블로킹 호출은 코루틴 자체 스레드 풀(기본 64)을 쓰므로, 이 풀이 새 상한이 됩니다 — 역시 상한이 어디로 갔는지 아는 것이 중요합니다.

이 가이드의 권고: MVC + 가상 스레드를 기본으로 두고, 코루틴은 "취소·타임아웃이 있는 팬아웃"이 실제로 필요한 자리에만 씁니다. 두 모델을 섞을 때는 runBlocking이 반드시 가상 스레드 위에서 호출되는지(플랫폼 스레드 풀 위에서 부르면 그 풀을 막습니다) 확인하세요.
