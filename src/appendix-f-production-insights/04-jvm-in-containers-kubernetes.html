04. 컨테이너 속 JVM과 Kubernetes — 메모리·GC·프로브·종료 예산

"힙은 절반도 안 썼는데 OOMKilled가 떴다", "배포마다 5xx가 몇 개씩 튄다", "DB가 잠깐 느려졌는데 파드가 전부 재시작됐다". 2026년 Kubernetes 위 Spring Boot 운영 글이 다루는 사고는 거의 이 셋입니다. 셋 모두 JVM이 아는 세계와 컨테이너 런타임이 아는 세계가 어긋나서 생깁니다. 이 페이지는 그 어긋남을 하나씩 맞춥니다. Phase 6-4·Phase 7-5에서 "무엇을 켜는지"를 배웠다면, 여기서는 "왜 그 숫자인지"를 다룹니다.

1. JVM 메모리는 힙만이 아니다

-XX:MaxRAMPercentage=75.0(Phase 6-2)이 왜 100이 아니라 75인지가 이 절의 전부입니다. 컨테이너의 메모리 제한(limits.memory)은 프로세스 전체의 RSS에 걸리지만, MaxRAMPercentage는 힙에만 걸립니다. 나머지 25%가 아래 항목들의 몫입니다.

# 힙 밖을 보는 도구 — 네이티브 메모리 추적 (NMT). 운영에서 잠깐 켜도 오버헤드 5~10%
JAVA_TOOL_OPTIONS="-XX:MaxRAMPercentage=75.0 -XX:NativeMemoryTracking=summary -XX:+ExitOnOutOfMemoryError"
# 실행 중 확인
jcmd <pid> VM.native_memory summary
  • -XX:+ExitOnOutOfMemoryError: 힙 OOM이 나면 JVM이 즉시 종료 → Kubernetes가 재시작. "반쯤 죽은 채로 readiness만 통과하는" 좀비 상태를 막습니다.
  • 가상 스레드 켠 뒤 메모리가 줄었다는 후기의 실체는 스레드 스택 예약이 사라진 것입니다. 힙이 아니라 RSS가 줍니다.
  • limit을 정할 때 힙 필요량 ÷ 0.75로 역산하고, Grafana에서 container_memory_working_set_bytes와 jvm.memory.used{area=heap}의 차이(= 힙 밖)를 한 달 추세로 봅니다.

2. CPU 제한과 스레드 수 — 스로틀링이라는 숨은 지연

JDK 10부터 JVM은 cgroup의 CPU quota를 읽어 availableProcessors()를 결정합니다. limits.cpu: 1000m이면 JVM은 1코어라고 믿고 GC 스레드·JIT 컴파일러 스레드·ForkJoinPool(가상 스레드의 캐리어!) 병렬성을 모두 1로 잡습니다. 반대로 requests.cpu: 250m만 있고 limit이 없으면 노드 코어 수 전체를 보고 스레드를 만듭니다.

설정JVM이 보는 코어일어나는 일
limits.cpu: 1000m1CFS 스로틀링: 100ms 주기에 100ms 쓰면 나머지 시간 정지. GC·JIT가 요청 스레드와 1코어를 다툼 → p99 지연 급증, 기동 시간 2~3배
limits.cpu: 2000m, requests: 500m2버스트 허용. 2026년 가장 흔한 절충
limit 없음 (requests만)노드 코어 수스로틀링 없음. 노드 공유 위험은 requests로 스케줄러가 관리. "CPU limit을 걷어내라"는 조류의 근거
-XX:ActiveProcessorCount=22 (강제)limit과 무관하게 JVM 스레드 수를 고정. limit 없이 쓸 때 스레드 폭증 방지

기동이 느리다면 CPU 스로틀링을 먼저 의심하세요. Spring 컨텍스트 초기화는 CPU 바운드이고 JIT도 이 시점에 가장 바쁩니다. 해법은 (a) limit 상향 또는 제거, (b) Phase 6-1의 CDS/AOT 캐시로 기동 시 할 일을 줄이기, (c) startup 프로브로 시간을 벌어 주기(§4)입니다.

3. 2026년의 GC 선택 — 기본은 G1, 바꿀 땐 이유와 함께

JDK 21에서 25로 넘어오며 GC 지형이 정리됐습니다. 핵심은 Generational ZGC가 "실험적 옵션"에서 "유일한 ZGC"가 된 것과 Compact Object Headers(JEP 519)입니다.

GC켜는 법강점대가Book API에서
G1 (기본)없음 (2코어·2GiB 이상이면 자동)처리량·RSS 균형. JDK 25에서 remembered set 메모리 60% 절감수백 ms 멈춤이 가끔 (힙 수 GB 이상에서)기본값 유지. 힙 4GiB 이하 서비스는 여기서 끝
Generational ZGCJDK 21: -XX:+UseZGC -XX:+ZGenerational
JDK 24+: -XX:+UseZGC (플래그 제거, 유일 모드)		멈춤 < 1ms. Netflix가 "GC 멈춤 사실상 0, 에러율 감소" 보고CPU 사용 ↑, 힙 25% 이상 헤드룸 필요, RSS ↑p99 지연 SLA가 있고 힙이 크면(8GiB+) 측정 후 전환
Generational Shenandoah-XX:+UseShenandoahGC (JEP 521, JDK 25 정식)ZGC와 유사한 저지연, 작은 힙에서도 무난배포판에 따라 미포함(Oracle JDK)ZGC 대안으로 벤치마크 후 결정

# JDK 25 기준 저지연 프로파일 — 반드시 운영과 같은 컨테이너 limit에서 부하 테스트 후 적용
JAVA_TOOL_OPTIONS="-XX:MaxRAMPercentage=75.0 -XX:+UseZGC -XX:+UseCompactObjectHeaders -XX:+ExitOnOutOfMemoryError"
# UseCompactObjectHeaders(JEP 519, JDK 25 정식): 객체 헤더 12→8바이트. 힙 5~10% 절감, 캐시 적중 ↑

GC를 바꾸는 유일한 정당한 이유는 측정입니다. 같은 컨테이너 limit, 같은 부하로 GC 멈춤 시간 · 할당률 · CPU 오버헤드 · RSS · p99 다섯 가지를 함께 비교하세요. ZGC는 멈춤을 없애는 대신 CPU와 메모리를 더 씁니다 — 그 CPU가 §2의 limit에 걸리면 오히려 느려집니다.

4. 프로브 3종 — 각각 다른 질문에 답한다

Kubernetes는 컨테이너에 세 가지 질문을 던지고, Spring Boot Actuator는 그 답을 Phase 5-3의 헬스 그룹으로 제공합니다. Kubernetes 위에서는 spring.main.cloud-platform이 자동 감지되어 /actuator/health/liveness·/readiness가 자동으로 켜집니다(다른 환경에서는 management.endpoint.health.probes.enabled=true).

프로브Actuator 경로포함할 것포함하지 말 것
startup/actuator/health/liveness (같은 경로, failureThreshold만 크게)컨텍스트 기동 완료—
readiness/actuator/health/readinessreadinessState + 없으면 요청을 처리할 수 없는 것(DB)외부 API, 캐시, 브로커(없어도 일부 기능은 됨 → 서킷 브레이커의 영역)
liveness/actuator/health/livenesslivenessState만 — "JVM이 응답하는가"모든 외부 의존성. 데드락·OOM처럼 재시작만이 답인 상태만
 
management:
  endpoint:
    health:
      probes:
        enabled: true                      # Kubernetes 밖(로컬·Cloud Run)에서도 같은 경로를 쓰려면
      group:
        readiness:
          include: readinessState,db       # DB 없으면 트래픽을 받지 않는다
        liveness:
          include: livenessState           # 절대 외부 의존성을 넣지 않는다
  endpoints:
    web:
      exposure:
        include: health,prometheus

5. 종료 예산 — 배포마다 5xx가 튀는 진짜 이유

Spring Boot 4는 그레이스풀 셧다운이 기본입니다(Phase 6-4). 그런데도 롤링 배포 때 5xx가 튄다면, 원인은 거의 항상 Kubernetes와 JVM의 타이머가 서로를 모르기 때문입니다. 파드가 종료될 때 두 시스템에서 동시에 벌어지는 일을 시간축에 놓아 보면:

세 숫자는 하나의 부등식으로 묶입니다.

terminationGracePeriodSeconds ≥ preStop sleep + timeout-per-shutdown-phase + 여유(5s)

예: 라우팅 전파 p99가 5초, 가장 긴 요청이 15초, 아웃박스 릴레이 한 배치가 3초라면 → preStop 5s, timeout-per-shutdown-phase 20s, grace 30s. 기본값 30s는 preStop 없이 딱 맞춰져 있어 preStop을 넣는 순간 부족해집니다.

# application.yml
server:
  shutdown: graceful                      # Boot 4 기본값 — 명시는 문서화 목적
spring:
  lifecycle:
    timeout-per-shutdown-phase: 20s       # 단계별 상한이지 보장은 아님 — 커스텀 SmartLifecycle이 있으면 더 걸릴 수 있다
# k8s/deployment.yaml — Book API
apiVersion: apps/v1
kind: Deployment
metadata:
  name: book-api
spec:
  replicas: 3
  strategy:
    rollingUpdate: { maxSurge: 1, maxUnavailable: 0 }     # 항상 3개는 살아 있게
  template:
    spec:
      terminationGracePeriodSeconds: 30                     # ≥ 5 (preStop) + 20 (shutdown phase) + 5
      containers:
        - name: book-api
          image: asia-northeast3-docker.pkg.dev/my-project/book-api/book-api:1.1.0
          ports: [{ containerPort: 8080 }]
          env:
            - name: JAVA_TOOL_OPTIONS
              value: "-XX:MaxRAMPercentage=75.0 -XX:+ExitOnOutOfMemoryError"
            - name: SPRING_PROFILES_ACTIVE
              value: prod
          resources:
            requests: { cpu: 500m, memory: 1Gi }
            limits:   { cpu: 2000m, memory: 1Gi }           # 메모리는 requests = limits (OOM 예측 가능), CPU는 버스트 허용
          lifecycle:
            preStop:
              sleep: { seconds: 5 }                         # K8s 1.30+ 네이티브 sleep — 이미지에 /bin/sh가 없어도 된다
          startupProbe:
            httpGet: { path: /actuator/health/liveness, port: 8080 }
            periodSeconds: 5
            failureThreshold: 30                            # 최대 150초 기동 허용 — CPU 스로틀링·콜드 스타트 대비
          readinessProbe:
            httpGet: { path: /actuator/health/readiness, port: 8080 }
            periodSeconds: 5
            failureThreshold: 3
          livenessProbe:
            httpGet: { path: /actuator/health/liveness, port: 8080 }
            periodSeconds: 10
            failureThreshold: 3
