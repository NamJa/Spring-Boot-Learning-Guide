02. 패키지 구조와 모듈러 모놀리스

앞 문서에서 S2의 문제는 성능이 아니라 사람 사이의 간섭이라고 했습니다. 이 문서는 그 간섭을 줄이는 가장 값싼 방법 — 경계를 코드로 그어 두는 것을 다룹니다.

1. 패키지를 나누는 두 가지 방식

이 가이드는 지금까지 계층 우선(layer-first) 구조를 썼습니다. controller, service, repository, dto… 입문에는 이게 최선입니다. "컨트롤러가 뭔지" 배우는 사람에게 컨트롤러가 한곳에 모여 있는 것보다 좋은 교재는 없으니까요.

그런데 도메인이 늘면 이 구조가 불리해집니다.

둘은 배타적이지 않습니다. 실무에서 가장 흔한 형태는 바깥은 도메인, 안쪽은 계층입니다 — catalog/controller, catalog/service 처럼요. 중요한 것은 최상위 분할 기준이 도메인이라는 점입니다. 그래야 폴더 하나가 곧 소유권 단위이자 추출 단위가 됩니다.

2. Book API가 서점으로 자란다면

부록 개요에서 말한 대로, 도서 API가 온라인 서점이 되어 세 영역을 갖게 되었다고 가정합니다.

문제는 이 규칙을 무엇이 지키게 하느냐입니다. 코드 리뷰에 맡기면 반드시 새어 나갑니다. 마감이 급한 금요일 저녁에 누군가 BookRepository를 직접 주입할 것이고, 아무도 눈치채지 못할 것입니다.

3. Spring Modulith — 경계를 테스트로 강제하기

Spring Modulith는 이 규칙을 실패하는 테스트로 바꿔 줍니다. 2026-08-30 기준 최신은 2.1.1(2026-08-26)이며, Spring Boot 4.1 / Spring Framework 7 위에서 빌드됩니다.

Spring Modulith는 Spring Boot BOM이 관리하지 않습니다. 별도 릴리스 트레인이므로 자체 BOM을 직접 import 해야 합니다. Boot 버전을 올릴 때 Modulith 버전도 함께 확인해야 하는 몇 안 되는 의존성 중 하나입니다.

kotlin
// build.gradle.kts
dependencies {
    // Spring Modulith BOM — Boot BOM이 관리하지 않으므로 직접 import
    implementation(platform("org.springframework.modulith:spring-modulith-bom:2.1.1"))

    implementation("org.springframework.modulith:spring-modulith-starter-core")
    // 모듈 간 이벤트를 DB에 기록해 유실을 막고 싶다면 (아웃박스)
    implementation("org.springframework.modulith:spring-modulith-starter-jpa")

    testImplementation("org.springframework.modulith:spring-modulith-starter-test")
}

기본 규칙은 애플리케이션 루트 패키지 바로 아래 한 단계가 하나의 모듈이라는 것입니다. 즉 위 트리에서 catalog·order·member가 자동으로 모듈이 되고, 그 하위 패키지는 전부 모듈 내부로 간주되어 다른 모듈에서 접근하면 위반입니다.

kotlin
package com.example.bookapi

import org.junit.jupiter.api.Test
import org.springframework.modulith.core.ApplicationModules
import org.springframework.modulith.docs.Documenter

class ModularityTests {

    private val modules = ApplicationModules.of(BookApiApplication::class.java)

    @Test
    fun `모듈 경계를 위반한 의존이 없다`() {
        modules.verify()   // 위반이 있으면 여기서 테스트가 깨진다
    }

    @Test
    fun `모듈 구조 문서를 생성한다`() {
        // Gradle 이면 build/spring-modulith-docs (Maven 이면 target/…) 아래에
        // PlantUML 다이어그램과 모듈 캔버스가 생성된다
        Documenter(modules).writeDocumentation()
    }
}

이제 누군가 order에서 catalog.internal.BookRepository를 주입하면 CI가 빨간불이 됩니다. 문서나 규약이 아니라 빌드가 규칙을 지킵니다.

의존을 명시적으로 좁히기

기본 규칙만으로는 "모든 모듈이 모든 모듈의 공개 타입을 쓸 수 있는" 상태입니다. 더 좁히려면 모듈에 허용 의존 목록을 선언합니다.

kotlin
package com.example.bookapi.order

import org.springframework.modulith.ApplicationModule

// Java 라면 package-info.java 에 붙이지만, Kotlin 에는 그런 파일이 없다.
// Spring Modulith 는 이 경우를 위해 "모듈 루트 패키지의 타입 하나"에 붙이는 것도 허용한다.
@ApplicationModule(
    displayName = "주문",
    allowedDependencies = ["catalog"],   // member 는 참조 금지
)
class OrderModuleMetadata

@ApplicationModule은 id·displayName·allowedDependencies·type 속성을 갖습니다. 모듈이 공개하는 타입을 더 세밀하게 고르고 싶다면 하위 패키지에 @NamedInterface를 붙여 "이 패키지만 공개 API" 라고 선언할 수 있습니다. 처음에는 기본 규칙만으로 시작하고, 실제로 새는 곳이 생길 때 좁히세요.

모듈 간 통신 — 호출인가 이벤트인가

이벤트 쪽을 고른다면 Spring Modulith의 @ApplicationModuleListener가 편합니다. 이것은 @TransactionalEventListener + @Async + @Transactional을 한 번에 붙인 것과 같아서, 발행 트랜잭션이 커밋된 뒤 별도 트랜잭션에서 비동기로 실행됩니다.

kotlin
package com.example.bookapi.catalog

import com.example.bookapi.order.OrderPlaced
import org.springframework.modulith.events.ApplicationModuleListener
import org.springframework.stereotype.Component

@Component
class StockUpdater(
    private val bookService: BookService,
) {
    // 주문이 커밋된 뒤에 실행 — 주문 트랜잭션을 재고 로직이 지연시키지 않는다
    @ApplicationModuleListener
    fun on(event: OrderPlaced) {
        bookService.decreaseStock(event.bookId, event.quantity)
    }
}

비동기 리스너는 애플리케이션이 죽으면 이벤트를 잃습니다. spring-modulith-starter-jpa를 넣으면 발행된 이벤트가 DB 테이블에 기록되고(이벤트 발행 레지스트리 = 아웃박스 패턴), 처리에 실패한 이벤트를 재발행할 수 있습니다. 재고·정산처럼 유실되면 안 되는 이벤트라면 이 스타터를 반드시 함께 씁니다.

더 가벼운 대안 — ArchUnit

Modulith까지는 부담스럽고 규칙 몇 개만 강제하고 싶다면 ArchUnit(2026-08-30 기준 1.5.0)으로 충분합니다. Modulith도 내부적으로 ArchUnit을 씁니다.

kotlin
import com.tngtech.archunit.core.importer.ClassFileImporter
import com.tngtech.archunit.lang.syntax.ArchRuleDefinition.noClasses
import org.junit.jupiter.api.Test

class ArchitectureTests {

    @Test
    fun `컨트롤러는 리포지토리를 직접 참조하지 않는다`() {
        val classes = ClassFileImporter().importPackages("com.example.bookapi")

        noClasses().that().resideInAPackage("..controller..")
            .should().dependOnClassesThat().resideInAPackage("..repository..")
            .check(classes)
    }
}

4. 헥사고날·어니언은 꼭 필요한가

모듈 이야기를 하면 반드시 따라오는 것이 헥사고날(포트&어댑터) 아키텍처입니다. 도메인을 가운데 두고, DB·웹·외부 API를 전부 인터페이스(포트) 뒤로 숨기는 구조죠.

이 구조가 주는 것은 분명합니다 — 도메인 코드가 프레임워크와 DB를 모르게 되고, 테스트가 빨라집니다. 그런데 지불하는 비용도 분명합니다.

컨퍼런스 인사이트 (Spring I/O 2026). Oliver Drotbohm은 Domain-centric? Why Hexagonal- and Onion-Architecture are answers to the wrong question 세션에서 이 유행을 정면으로 문제 삼았습니다. 그가 던진 질문은 "이 연습의 실제 목표가 무엇이고, 꼭 이렇게 복잡해야 하는가" 입니다. 세션은 도메인 모델이 영속성 메타데이터를 담아도 되는가, 추상화는 얼마나 필요한가 를 구체적으로 따지고, 결론적으로 레이어를 겹겹이 두는 것보다 "모듈 경계를 도구로 강제하는 것"이 대부분의 목적을 더 싸게 달성한다는 쪽에 섭니다. 헥사고날을 쓰지 말라는 뜻이 아니라, 남들이 하니까 하는 것을 멈추라는 뜻입니다.

실용적인 절충안은 이렇습니다.

상황 권장
대부분의 CRUD·업무 시스템 모듈 경계만 — JPA 엔티티를 도메인 모델로 그대로 쓰고, 모듈 밖으로는 DTO만 내보낸다
외부 시스템 연동이 많고 실제로 교체된다 연동 지점에만 포트 인터페이스 — 전면 헥사고날이 아니라 필요한 곳만
도메인 규칙이 복잡하고 오래 유지된다 (결제·정산·보험) 도메인 모델 분리가 값을 한다. 매핑 비용을 내고도 남는다

5. 언제, 어떻게 서비스로 꺼내나

모듈 경계가 자리를 잡으면 추출은 기술 작업이 됩니다. 순서가 중요합니다.

정리

  • 도메인이 3개를 넘고 팀이 2개 이상이면 계층 우선 → 도메인 우선 패키지로 옮길 때입니다.
  • 경계는 규약이 아니라 테스트로 지킵니다 — Spring Modulith modules.verify() 또는 ArchUnit.
  • 모듈 간 통신은 같은 트랜잭션이 필요한가로 갈립니다. 이벤트를 쓴다면 유실 대비(아웃박스)를 함께 준비합니다.
  • 헥사고날은 목적이 있을 때만. 대부분은 모듈 경계만으로 목적의 대부분을 달성합니다.
  • 서비스 추출의 진짜 관문은 코드가 아니라 DB 테이블 소유권입니다.
