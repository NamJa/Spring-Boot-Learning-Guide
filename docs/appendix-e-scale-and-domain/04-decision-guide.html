3. 자주 보는 안티패턴

안티패턴 이렇게 보인다 대신
분산 모놀리스 서비스는 5개인데 기능 하나 추가에 5개를 다 배포한다. 서비스들이 같은 DB 테이블을 쓴다 모듈 경계를 먼저 잡고(02), 테이블 소유권이 갈린 뒤에 배포를 나눈다
추측 튜닝 느리다는 제보에 캐시부터 붙인다. 빨라졌는지 아무도 모른다 측정 → 원인 → 조치 → 재측정. 메트릭이 먼저다
인터페이스 증식 BookService / BookServiceImpl. 구현체는 영원히 하나 구현이 하나면 클래스 하나로 충분하다. 두 번째 구현이 실제로 생길 때 인터페이스를 뽑는다
이벤트 만능주의 같은 트랜잭션에서 끝나야 할 일까지 이벤트로 던진다. 어디서 실패했는지 추적이 안 된다 같은 트랜잭션이 필요하면 그냥 호출한다 (02-3의 분기)
공통 라이브러리 조기 추출 서비스 2개가 생기자마자 common 모듈을 만든다. 이제 모든 서비스가 그 버전에 묶인다 중복을 세 번 볼 때까지 기다린다. 공유 모듈은 결합이지 재사용이 아니다
Boot 3 예제 복사 @MockBean·spring-boot-starter-web·com.fasterxml.jackson이 컴파일되지 않는다 기준 버전 표와 각 Phase의 경고 박스를 확인 (Boot 4에서 이름·패키지가 바뀐 것들)
트랜잭션 안 외부 호출 평소엔 멀쩡하다가 외부 API가 느린 날 커넥션 풀이 마르고 전체가 멈춘다 외부 호출은 트랜잭션 바깥으로. 타임아웃은 필수 (Phase 5-1)

5. 이 부록의 결론

설계에 정답은 없지만 순서는 있습니다.

측정 → 코드로 고치기 → 경계 긋기 → 배포 나누기. 이 순서를 지키면 대부분의 결정이 되돌릴 수 있는 상태로 남습니다. 순서를 뒤집으면 — 측정 없이 인프라를 붙이고, 경계 없이 배포를 나누면 — 되돌릴 수 없는 복잡도만 남습니다.

2026년 Spring 커뮤니티가 모듈러 모놀리스와 도구로 강제하는 경계를 다시 이야기하는 이유가 여기에 있습니다. 마이크로서비스가 틀렸다는 것이 아니라, 그 앞에 건너뛴 단계가 있었다는 뒤늦은 합의입니다.
