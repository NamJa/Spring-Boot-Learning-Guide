03. 신뢰성 패턴 — 아웃박스·멱등성·재시도·속도 제한

2025년 말~2026년 Medium에서 "이벤트 기반 Spring Boot"를 다룬 글들은 놀랍도록 같은 청사진에 수렴했습니다. 트랜잭셔널 아웃박스 + Kafka + 멱등 소비자. 국내에서도 29CM의 아웃박스 구현 사례가 LinkedIn·velog에서 여전히 인용됩니다. 이 페이지는 그 청사진을 왜 그렇게 수렴했는지(CS)부터 설명하고, Book API가 서점으로 자란 상황(order → catalog 재고 차감)에 그대로 적용합니다.

1. 왜 "정확히 한 번"은 없나 (CS)

네트워크 위에서 두 참여자가 있으면 "상대가 내 메시지를 받았는지"를 확신할 수 없는 순간이 항상 존재합니다(두 장군 문제). 요청은 갔는데 응답이 유실되면 보낸 쪽은 재시도하고, 받은 쪽은 두 번 처리합니다. 재시도하지 않으면 유실됩니다. 그래서 전달 보장은 둘 중 하나입니다.

보장의미대가
at-most-once재시도 안 함. 유실될 수 있음로그·메트릭처럼 잃어도 되는 것에만
at-least-once확인될 때까지 재시도. 중복될 수 있음받는 쪽이 멱등해야 함 — 이 페이지의 주제
exactly-once정확히 한 번분산 시스템 일반에는 존재하지 않음. Kafka의 "exactly-once"는 Kafka 안(토픽→토픽)에서만 성립

2. 아웃박스 — 두 개의 쓰기를 하나의 커밋으로

주문을 저장하고(DB) 이벤트를 발행하는(Kafka) 것은 두 시스템에 대한 두 번의 쓰기(dual-write)입니다. DB 커밋 후 브로커 발행이 실패하면 주문은 있는데 이벤트가 없고, 순서를 바꾸면 이벤트는 갔는데 주문이 롤백됩니다. 아웃박스는 이벤트를 같은 DB 트랜잭션 안의 테이블에 적고, 별도 릴레이가 브로커로 옮깁니다.

2.1 옵션 A — 이미 갖고 있는 아웃박스: Spring Modulith

부록 E-02에서 붙인 spring-modulith-starter-jpa의 이벤트 발행 레지스트리가 바로 아웃박스입니다. 모듈 안에서는 @ApplicationModuleListener가 소비하고, 외부(Kafka)로도 내보내야 한다면 이벤트 클래스에 @Externalized 한 줄을 붙입니다.

kotlin
// build.gradle.kts — 부록 E-02의 Modulith 설정에 추가
implementation("org.springframework.modulith:spring-modulith-events-api")
implementation("org.springframework.modulith:spring-modulith-events-kafka")   // Kafka로 외부화
implementation("org.springframework.kafka:spring-kafka")
kotlin
package com.example.bookapi.order

import org.springframework.modulith.events.Externalized

// "orders.placed" 토픽으로, 키는 orderId — 같은 주문의 이벤트는 같은 파티션(순서 보장)
@Externalized("orders.placed::#{orderId}")
data class OrderPlaced(val orderId: Long, val bookId: Long, val quantity: Int)
kotlin
package com.example.bookapi.order

import org.springframework.context.ApplicationEventPublisher
import org.springframework.stereotype.Service
import org.springframework.transaction.annotation.Transactional

@Service
class OrderService(
    private val orderRepository: OrderRepository,
    private val events: ApplicationEventPublisher,
) {
    @Transactional
    fun place(request: PlaceOrderRequest): OrderResponse {
        val order = orderRepository.save(Order.from(request))
        events.publishEvent(OrderPlaced(order.id, order.bookId, order.quantity))  // 같은 트랜잭션에서 레지스트리에 기록
        return order.toResponse()
    }
}

커밋되면 Modulith가 레지스트리에서 이벤트를 읽어 Kafka로 보내고, 성공하면 완료 표시를 합니다. 실패하면 미완료로 남아 재시작 시 재발행됩니다(그래서 at-least-once). 2026년 현재 모듈러 모놀리스에서 아웃박스를 직접 구현할 이유는 거의 없습니다.

2.2 옵션 B — 직접 구현해야 할 때

Modulith를 쓰지 않거나, 페이로드 스키마·정리 정책·백로그 관측을 세밀하게 제어해야 한다면 직접 구현합니다. 2026년 글들이 강조하는 것은 "아웃박스는 테이블 하나가 아니라 작은 운영 서브시스템이다"라는 점입니다. 릴레이·중복·순서·백로그·정리 정책을 브로커 장애가 시험하기 전에 명시해야 합니다.

sql
-- Flyway V5__outbox.sql
CREATE TABLE outbox_event (
    id             UUID PRIMARY KEY,
    aggregate_type VARCHAR(50)  NOT NULL,     -- 'Order'
    aggregate_id   VARCHAR(50)  NOT NULL,     -- '42'  → Kafka 파티션 키
    event_type     VARCHAR(100) NOT NULL,     -- 'OrderPlaced'
    payload        JSONB        NOT NULL,
    created_at     TIMESTAMPTZ  NOT NULL DEFAULT now(),
    published_at   TIMESTAMPTZ                -- NULL = 미발행
);
CREATE INDEX outbox_unpublished_idx ON outbox_event (created_at) WHERE published_at IS NULL;
kotlin
package com.example.bookapi.order

import org.springframework.data.jpa.repository.JpaRepository
import org.springframework.data.jpa.repository.Query

interface OutboxEventRepository : JpaRepository<OutboxEvent, java.util.UUID> {
    // SKIP LOCKED: 릴레이가 여러 인스턴스에서 돌아도 같은 행을 두 번 집지 않는다
    @Query(
        value = """SELECT * FROM outbox_event WHERE published_at IS NULL
                   ORDER BY created_at LIMIT 100 FOR UPDATE SKIP LOCKED""",
        nativeQuery = true,
    )
    fun lockNextBatch(): List<OutboxEvent>

    fun deleteByPublishedAtBefore(threshold: java.time.Instant): Long
}
kotlin
package com.example.bookapi.order

import org.springframework.kafka.core.KafkaTemplate
import org.springframework.scheduling.annotation.Scheduled
import org.springframework.stereotype.Component
import org.springframework.transaction.annotation.Transactional
import java.time.Instant

@Component
class OutboxRelay(
    private val outbox: OutboxEventRepository,
    private val kafka: KafkaTemplate<String, String>,
) {
    @Scheduled(fixedDelay = 500)
    @Transactional                       // 락 → 전송 → published_at 갱신을 한 트랜잭션으로
    fun relay() {
        outbox.lockNextBatch().forEach { e ->
            kafka.send("orders.placed", e.aggregateId, e.payload).get()   // 동기 확인 — 실패하면 예외 → 롤백 → 다음 주기에 재시도
            e.publishedAt = Instant.now()
        }
    }

    @Scheduled(cron = "0 0 4 * * *")     // 발행 7일 지난 행 정리 — 테이블이 커지면 인덱스가 아닌 정리 정책이 답
    @Transactional
    fun cleanup() = outbox.deleteByPublishedAtBefore(Instant.now().minus(java.time.Duration.ofDays(7)))
}

운영 항목 네 가지를 미리 정하세요. ① 백로그 메트릭: published_at IS NULL 행 수와 최고령 행의 나이를 Micrometer 게이지로. ② 순서: 파티션 키를 애그리거트 ID로 — 전체 순서는 포기하고 같은 주문 안의 순서만 보장. ③ 폴링 vs CDC: 폴링은 단순하고 500ms 지연, Debezium CDC는 지연이 낮지만 운영 요소가 하나 더. S2 이후에 고민. ④ Cloud Run처럼 요청 없을 때 CPU를 주지 않는 플랫폼에서는 @Scheduled 릴레이가 멈춥니다 — "CPU 항상 할당" 설정 또는 Cloud Scheduler로 릴레이 엔드포인트를 깨워야 합니다(04).

3. 멱등 소비자 — 인박스 테이블

at-least-once로 도착한 OrderPlaced가 두 번 오면 재고를 두 번 차감합니다. 소비자는 처리한 이벤트 ID를 자기 트랜잭션 안에 기록해야 합니다. 이벤트마다 불변의 event_id가 있어야 하고(아웃박스 id가 그 역할), 비멱등 부작용을 내는 모든 소비자는 자기 연산 범위의 중복 제거 전략이 필요합니다.

sql
-- catalog 모듈 소유 — "이 소비자가" 처리한 이벤트
CREATE TABLE processed_event (
    event_id     UUID PRIMARY KEY,
    consumer     VARCHAR(100) NOT NULL,
    processed_at TIMESTAMPTZ  NOT NULL DEFAULT now()
);
kotlin
package com.example.bookapi.catalog

import org.springframework.dao.DuplicateKeyException
import org.springframework.jdbc.core.simple.JdbcClient
import org.springframework.kafka.annotation.KafkaListener
import org.springframework.kafka.support.KafkaHeaders
import org.springframework.messaging.handler.annotation.Header
import org.springframework.stereotype.Component
import org.springframework.transaction.annotation.Transactional
import java.util.UUID

@Component
class OrderPlacedConsumer(
    private val jdbc: JdbcClient,
    private val inventoryService: InventoryService,
) {
    @KafkaListener(topics = ["orders.placed"], groupId = "catalog")
    @Transactional                                   // 중복 기록 + 재고 차감이 하나의 트랜잭션
    fun on(event: OrderPlacedMessage, @Header(KafkaHeaders.RECEIVED_KEY) key: String) {
        try {
            jdbc.sql("INSERT INTO processed_event (event_id, consumer) VALUES (:id, 'catalog.stock')")
                .param("id", UUID.fromString(event.eventId)).update()
        } catch (dup: DuplicateKeyException) {
            return                                   // 이미 처리한 이벤트 — 조용히 무시 (멱등)
        }
        inventoryService.decrease(event.bookId, event.quantity)   // 재고 차감은 @Version 또는 CHECK(stock >= 0)로 보호 (02)
    }
}

재고 차감처럼 연산 자체를 멱등하게 만들 수 있으면 인박스 테이블이 필요 없습니다. "재고를 3 줄여라"는 멱등하지 않지만 "주문 42의 재고 예약을 확정하라"는 멱등합니다(이미 확정됐으면 아무 일도 안 함). 메시지를 명령(delta)이 아니라 사실(fact)로 설계하면 중복이 덜 아픕니다.

4. HTTP 멱등 키 — POST도 안전하게 재시도

§1의 시나리오(응답 유실 후 재시도)는 브로커가 아니라 HTTP에서 일어났습니다. Stripe가 대중화하고 IETF 초안(Idempotency-Key 헤더)으로 정리된 방식: 클라이언트가 요청마다 고유 키를 보내고, 서버는 키 → 응답을 저장해 두었다가 같은 키가 오면 저장된 응답을 그대로 돌려줍니다. 2026년에는 AI 에이전트가 API를 호출하며 재시도를 훨씬 공격적으로 하기 때문에 중요도가 더 올라갔습니다(05).

kotlin
package com.example.bookapi.order

import org.springframework.dao.DataIntegrityViolationException
import org.springframework.http.HttpStatus
import org.springframework.http.ResponseEntity
import org.springframework.web.bind.annotation.*

@RestController
@RequestMapping("/api/orders")
class OrderController(
    private val orderService: OrderService,
    private val idempotency: IdempotencyStore,       // key → (status, body) 를 24h TTL로 저장 (Redis 또는 UNIQUE 컬럼 테이블)
) {
    @PostMapping
    fun place(
        @RequestHeader("Idempotency-Key") key: String,
        @RequestBody request: PlaceOrderRequest,
    ): ResponseEntity<OrderResponse> {
        idempotency.find(key)?.let { return it.toResponseEntity() }          // 이미 처리 → 같은 응답 재전송

        val response = try {
            orderService.place(request)
        } catch (e: DataIntegrityViolationException) {                        // 동시에 같은 키로 두 요청이 들어온 경합
            return idempotency.find(key)!!.toResponseEntity()
        }
        idempotency.save(key, HttpStatus.CREATED, response)
        return ResponseEntity.status(HttpStatus.CREATED).body(response)
    }
}

세부 규칙: 키의 범위는 클라이언트(회원)별로 잡고(다른 회원이 같은 UUID를 보낼 수 있음), 같은 키에 다른 본문이 오면 422로 거절하며, 처리 중인 키가 다시 오면 409로 "진행 중"을 알립니다. 이 규칙들이 IETF 초안의 골자입니다.

5. 재시도 — 지터 없는 재시도는 자기 DDoS

다운스트림이 잠깐 느려질 때 모든 클라이언트가 정확히 1초 후 재시도하면, 1초 뒤 부하는 원래의 2배가 됩니다(thundering herd). 해법은 두 가지를 동시에 쓰는 것입니다. 지수 백오프(간격을 2배씩)로 간격을 벌리고, 지터(무작위 흩뜨림)로 시점을 분산합니다. Phase 5-1의 @Retryable에 jitter가 있는 이유입니다.

kotlin
package com.example.bookapi.client

import org.springframework.resilience.annotation.Retryable
import org.springframework.stereotype.Component
import org.springframework.web.client.HttpServerErrorException
import org.springframework.web.client.ResourceAccessException

@Component
class PublisherClient(private val api: PublisherApi) {

    // 5xx·타임아웃만 재시도. 4xx(우리 잘못)는 재시도해도 같은 결과 — includes로 명시
    @Retryable(
        includes = [HttpServerErrorException::class, ResourceAccessException::class],
        maxRetries = 3,        // 총 4회 시도
        delay = 200,           // 첫 대기 200ms
        multiplier = 2.0,      // 200 → 400 → 800
        jitter = 100,          // 각 대기에 ±100ms 무작위
        maxDelay = 2000,
    )
    fun fetch(isbn: String): PublisherBook = api.book(isbn)
}

재시도는 멱등한 호출에만. 결제 승인 POST를 재시도하면 이중 결제가 됩니다 — 그 호출에 §4의 멱등 키를 붙인 뒤에야 재시도가 안전해집니다. 그리고 재시도는 호출 체인의 한 층에서만 하세요. 게이트웨이 3회 × 서비스 3회 × 클라이언트 3회 = 27배 부하입니다.

6. 속도 제한과 동시성 상한

재시도·멱등성이 "우리가 남을 부르는" 쪽의 규율이라면, 속도 제한은 "남이 우리를 부르는" 쪽의 방어입니다. 두 개념을 구분해야 합니다.

동시성 상한 (concurrency limit)속도 제한 (rate limit)
재는 것지금 동시에 실행 중인 수시간당 허용 횟수 (예: 분당 100회)
보호 대상우리 자원(풀·메모리·CPU) — 가상 스레드가 없앤 상한을 복원공정성·과금·남용 방지 — 클라이언트별
Spring에서@ConcurrencyLimit(n) — Framework 7 내장, 인스턴스 단위토큰 버킷 — Bucket4j(8.19, bucket4j_jdk17-core), 여러 인스턴스면 Redis 백엔드
초과 시기본 대기(BLOCK). ConcurrencyThrottleInterceptor429 Too Many Requests + Retry-After 헤더
kotlin
package com.example.bookapi.config

import io.github.bucket4j.Bandwidth
import io.github.bucket4j.Bucket
import jakarta.servlet.FilterChain
import jakarta.servlet.http.HttpServletRequest
import jakarta.servlet.http.HttpServletResponse
import org.springframework.stereotype.Component
import org.springframework.web.filter.OncePerRequestFilter
import java.time.Duration
import java.util.concurrent.ConcurrentHashMap

// ponytail: 인스턴스별 메모리 버킷. 인스턴스가 여럿이면 bucket4j-redis(Lettuce) ProxyManager로 교체
@Component
class RateLimitFilter : OncePerRequestFilter() {
    private val buckets = ConcurrentHashMap<String, Bucket>()

    private fun bucketFor(apiKey: String) = buckets.computeIfAbsent(apiKey) {
        Bucket.builder()
            .addLimit(Bandwidth.builder().capacity(100).refillGreedy(100, Duration.ofMinutes(1)).build())
            .build()
    }

    override fun doFilterInternal(req: HttpServletRequest, res: HttpServletResponse, chain: FilterChain) {
        val key = req.getHeader("X-API-Key") ?: req.remoteAddr
        val probe = bucketFor(key).tryConsumeAndReturnRemaining(1)
        if (probe.isConsumed) {
            res.setHeader("X-RateLimit-Remaining", probe.remainingTokens.toString())
            chain.doFilter(req, res)
        } else {
            res.status = 429
            res.setHeader("Retry-After", (probe.nanosToWaitForRefill / 1_000_000_000).coerceAtLeast(1).toString())
        }
    }
}

토큰 버킷은 버스트를 허용합니다(버킷이 가득 차 있으면 순간 100회 가능). 균등한 간격을 강제하려면 leaky bucket이나 refillIntervally를 씁니다. 그리고 속도 제한은 게이트웨이(Cloud Armor, API Gateway, Ingress)에서 먼저 하고, 애플리케이션 계층은 비즈니스 규칙(요금제별 한도)만 맡는 것이 2026년의 일반적 배치입니다.
