1. 왜 "인사이트"를 따로 모았나

공식 문서는 기능이 무엇인지는 알려 주지만, 운영에서 어떤 순서로 무엇이 무너지는지는 알려 주지 않습니다. 그 정보는 현장 후기에만 있습니다. 예를 들어 2026년 Medium에서 가장 많이 읽힌 Spring 글 중 하나는 "Virtual Threads Made My Spring App Faster — Then Production Happened" 류의 후기입니다. 요지는 한결같습니다. 가상 스레드는 스레드 병목을 없애는 대신, 그 뒤에 숨어 있던 진짜 병목(커넥션 풀·외부 API·락)을 드러낸다는 것입니다. 이런 것은 문서에 없습니다.

이 부록의 한 문장 결론: 성능·신뢰성 문제의 대부분은 어딘가에 있던 상한(스레드 수·풀 크기·TTL·타임아웃)이 사라지거나 어긋나서 생깁니다. 새 기술을 켤 때는 "이 기술이 어떤 상한을 없애는가, 그러면 그 다음 상한은 어디인가"를 먼저 물으세요.

2. 이 부록의 구성

  1. 01. 가상 스레드 실전 — OS 스레드의 비용(CS), 피닝과 JDK 24의 해결, ThreadLocal 팽창과 JDK 25 Scoped Values, 병목의 이동, 구조적 동시성 vs Kotlin 코루틴.
  2. 02. 데이터 계층 운영 — HikariCP 사이징 공식과 그 근거, Boot 4.1 지연 커넥션, L1/L2 캐시와 스탬피드 방어, 낙관적 락 → 비관적 락 → 분산 락의 선택 순서.
  3. 03. 신뢰성 패턴 — dual-write 문제와 아웃박스(Modulith 재활용 vs 직접 구현), 멱등 소비자와 Idempotency-Key, 지터 있는 재시도, 동시성 상한과 토큰 버킷.
  4. 04. 컨테이너 속 JVM과 Kubernetes — 힙 밖 메모리, cgroup CPU와 스레드 수, 2026년 GC 선택(G1 vs Generational ZGC), 프로브 3종, 종료 예산 산식, Cloud Run과의 대응.
  5. 05. 2026 스택 레이더 — OpenTelemetry 스타터, Boot 4.1 gRPC 자동 설정, Spring AI 2.0 MCP 서버, Spring Security 7 Passkeys·SSRF 방어. 채택/시범/관망 판정.

3. 선수 지식

  • Phase 0-5 — MVC vs WebFlux와 가상 스레드 소개. 01은 거기서 한 줄로 켠 설정의 뒷면입니다.
  • Phase 3 — 트랜잭션과 PostgreSQL 설정. 02·03은 트랜잭션 경계를 전제로 합니다.
  • Phase 5-3 — Actuator·관측성. 04의 프로브와 05의 OpenTelemetry가 이를 확장합니다.
  • Phase 6·7 — 배포·운영과 Cloud Run 운영. 04는 이를 Kubernetes 관점에서 다시 봅니다.
  • 부록 E — 규모 단계 S0~S3. 이 부록의 모든 "언제 도입하나"는 이 단계를 기준으로 답합니다.

예제는 계속 Book API(com.example.bookapi)이며, 부록 E처럼 서점으로 자란 상황(catalog · order · member)을 필요할 때만 가정합니다. 버전 기준은 Spring Boot 4.1.1 · Spring Framework 7.0.9 · JDK 21(JDK 25 기능은 그렇게 표시)입니다. 인용한 글의 출처는 각 페이지 끝 더 읽을거리에 모았습니다.
