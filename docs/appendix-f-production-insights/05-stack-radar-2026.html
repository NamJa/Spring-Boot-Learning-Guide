05. 2026 스택 레이더 — OpenTelemetry·gRPC·Spring AI·Passkeys

2026년 상반기는 Spring 생태계에 "직접 붙이던 것이 프레임워크 기능이 된" 해였습니다. Spring Boot 4.1(6월 10일)은 gRPC 자동 설정과 SSRF 방어를, Spring AI 2.0(6월 12일 GA)은 MCP 서버 애너테이션을, Spring Security 7은 Passkeys와 MFA를 들고 왔습니다. LinkedIn·Medium의 "2026 백엔드 트렌드" 글들이 공통으로 꼽는 것도 이 넷입니다. 이 페이지는 각각을 Book API에 붙이면 어떻게 되는지 보여 주고, 마지막에 채택 / 시범 / 관망 판정을 내립니다.

1. OpenTelemetry 스타터 — 세 신호, 한 형식

Phase 5-3에서는 Micrometer Tracing 브리지와 OTLP 익스포터를 직접 조합했습니다. Boot 4.0부터는 그 조합이 spring-boot-starter-opentelemetry 하나로 묶였고(start.spring.io에서 "OpenTelemetry" 선택), 4.1에서 샘플러·한도·exemplar 설정이 추가됐습니다. 의미는 벤더 중립입니다 — 메트릭·추적·로그가 OTLP라는 한 와이어 포맷으로 나가므로 Collector 뒤의 백엔드(Grafana Tempo, Jaeger, Datadog, Cloud Trace)를 바꿔도 앱은 그대로입니다.

kotlin
// build.gradle.kts — Phase 5-3의 두 줄(bridge-otel + exporter-otlp)을 이 한 줄로 대체
implementation("org.springframework.boot:spring-boot-starter-opentelemetry")
// 로그까지 OTLP로 보내려면 (아직 alpha 표기) — Logback 어펜더
implementation("io.opentelemetry.instrumentation:opentelemetry-logback-appender-1.0:2.21.0-alpha")
yaml
management:
  opentelemetry:
    enabled: true                                    # 4.1: 한 스위치로 전체 on/off
    resource-attributes:
      service.name: book-api
      deployment.environment: prod
    tracing:
      export:
        otlp:
          endpoint: http://otel-collector:4318/v1/traces
      sampler: parent-based-trace-id-ratio           # 4.1: 샘플러 선택
    logging:
      export:
        otlp:
          endpoint: http://otel-collector:4318/v1/logs
  otlp:
    metrics:
      export:
        url: http://otel-collector:4318/v1/metrics   # 메트릭은 Micrometer OTLP 레지스트리 경로
        compression-mode: gzip                       # 4.1
  tracing:
    sampling:
      probability: 0.1                               # 운영 10% — sampler가 ratio 계열일 때 사용
    exemplars:
      filter: trace-based                            # 4.1: 메트릭 ↔ 추적 연결(exemplar)

비동기 경계에서 trace가 끊긴다면 4.1의 @Async 컨텍스트 자동 전파가 처리합니다. 직접 만든 Executor가 있다면 ContextPropagatingTaskDecorator를 빈으로 등록하세요. 그리고 추적이 자동으로 붙는 것은 Spring이 만들어 준 클라이언트(RestClient.Builder 주입, HTTP 인터페이스)뿐입니다. RestClient.create()로 직접 만들면 span이 끊깁니다.

2. gRPC — Boot 4.1의 자동 설정

Book API가 서점으로 자라 order와 catalog가 별도 서비스가 되는 순간(S3), 서비스 간 호출을 REST/JSON으로 할지 gRPC로 할지 결정해야 합니다. 2026년 6월 Boot 4.1이 Spring gRPC 1.1을 공식 스타터로 흡수하면서 "붙이는 비용"이 크게 줄었습니다.

관점(CS)REST + JSONgRPC + Protobuf
전송HTTP/1.1 또는 2, 텍스트HTTP/2 필수 — 한 연결에 다중 스트림(멀티플렉싱), 헤더 압축
직렬화JSON — 사람이 읽음, 필드명 반복, 파싱 비용바이너리, 필드 번호로 식별 → 크기 1/3~1/10, 파싱 수 배 빠름
계약OpenAPI(선택).proto가 곧 계약. 코드 생성으로 클라이언트·서버 타입 일치 강제
스키마 진화필드 추가는 쉬움, 이름 변경은 깨짐번호를 재사용하지 않으면 양방향 호환. 이름은 자유롭게 변경
스트리밍SSE·WebSocket 별도단방향·양방향 스트리밍이 1급 기능
브라우저·공개 API자연스러움grpc-web 프록시 필요 → 외부 공개엔 부적합

package com.example.bookapi.catalog

import com.example.bookapi.catalog.grpc.CatalogGrpc
import com.example.bookapi.catalog.grpc.GetStockRequest
import com.example.bookapi.catalog.grpc.StockReply
import io.grpc.stub.StreamObserver
import org.springframework.grpc.server.service.GrpcService

@GrpcService                                       // BindableService 빈이면 자동 노출
class CatalogGrpcService(private val inventoryService: InventoryService) : CatalogGrpc.CatalogImplBase() {
    override fun getStock(request: GetStockRequest, responseObserver: StreamObserver<StockReply>) {
        val qty = inventoryService.stockOf(request.bookId)
        responseObserver.onNext(StockReply.newBuilder().setBookId(request.bookId).setQuantity(qty).build())
        responseObserver.onCompleted()
    }
}

3. Spring AI 2.0 — Book API를 MCP 도구로

2026년 LinkedIn·Medium의 트렌드 글이 가장 많이 반복한 문장은 "AI 에이전트가 API의 새로운 클라이언트다"입니다. 사람이 화면에서 누르던 "도서 검색"을 에이전트가 도구 호출로 수행합니다. 그 표준 프로토콜이 MCP(Model Context Protocol)이고, Spring AI 2.0(2026-06-12 GA, Boot 4.1 · Framework 7 필수)은 MCP 서버를 애너테이션 하나로 만듭니다. 커뮤니티 인큐베이터에 있던 @McpTool 계열이 코어로 편입됐고, 전송은 Streamable HTTP가 기본(SSE는 deprecated)입니다.

kotlin
// build.gradle.kts
dependencies {
    implementation(platform("org.springframework.ai:spring-ai-bom:2.0.1"))            // Boot BOM 관리 대상 아님
    implementation("org.springframework.ai:spring-ai-starter-mcp-server-webmvc")      // MVC 위 Streamable HTTP / SSE / Stateless
}
yaml
spring:
  ai:
    mcp:
      server:
        name: book-api
        version: 1.1.0
        type: SYNC
        protocol: STREAMABLE                  # STREAMABLE | SSE | STATELESS
        annotation-scanner:
          enabled: true
kotlin
package com.example.bookapi.mcp

import com.example.bookapi.service.BookService
import org.springframework.stereotype.Component
// MCP 애너테이션 import 생략 — Spring AI 2.0 코어 (@McpTool, @McpToolParam, @McpResource)

@Component
class BookTools(private val bookService: BookService) {

    // JSON 스키마는 시그니처와 @McpToolParam 설명에서 자동 생성 — 별도 스키마 파일 없음
    @McpTool(name = "search_books", description = "제목·저자 키워드로 도서를 검색한다. 최대 20건")
    fun searchBooks(
        @McpToolParam(description = "검색 키워드", required = true) keyword: String,
    ): List<BookResponse> = bookService.search(keyword, limit = 20)

    @McpTool(name = "get_book", description = "도서 ID로 상세 정보를 조회한다")
    fun getBook(@McpToolParam(description = "도서 ID", required = true) id: Long): BookResponse =
        bookService.getBook(id)

    @McpResource(uri = "book://{id}", name = "book", description = "도서 한 권의 상세 (읽기 전용)")
    fun bookResource(id: String): String = bookService.getBook(id.toLong()).toJson()
}

중요한 것은 기존 BookService를 그대로 재사용했다는 점입니다. MCP 도구는 컨트롤러와 같은 층의 또 하나의 어댑터입니다. 그래서 부록 E-02의 "서비스 계층에 비즈니스 규칙을 모아라"는 원칙이 여기서 보상을 받습니다.

에이전트 클라이언트가 바꾸는 운영 전제 세 가지. ① 에이전트는 실패하면 즉시·반복적으로 재시도합니다 → 03의 Idempotency-Key와 속도 제한이 선택이 아닌 필수. ② 에이전트가 URL을 인자로 넘기는 도구(예: "이 링크의 도서 정보를 가져와")는 SSRF의 정석 경로 → §4의 InetAddressFilter. ③ 도구 설명(description)이 곧 API 문서입니다 — 모호하면 에이전트가 잘못 호출합니다. 2026년의 "No-BS" 평가들은 Spring AI를 "Spring 팀이 만든 AI 통합"으로 자리매김하되, 다중 에이전트 오케스트레이션은 아직 평가 단계로 봅니다.

4. Spring Security 7 — Passkeys · MFA · SSRF 방어

4.1 Passkeys(WebAuthn) — 비밀번호 없는 로그인

부록 D-04의 폼 로그인에 Passkeys를 더하면 비밀번호 유출·피싱이 원리적으로 사라집니다(공개키 암호, 출처(origin) 바인딩). Spring Security 7은 이를 1급 기능으로 넣었고, Kotlin DSL도 지원합니다.

kotlin
// build.gradle.kts
implementation("org.springframework.security:spring-security-webauthn")
kotlin
package com.example.bookapi.config

import org.springframework.context.annotation.Bean
import org.springframework.context.annotation.Configuration
import org.springframework.security.config.annotation.web.builders.HttpSecurity
import org.springframework.security.config.annotation.web.invoke
import org.springframework.security.web.SecurityFilterChain

@Configuration(proxyBeanMethods = false)
class WebAuthnSecurityConfig {
    @Bean
    fun filterChain(http: HttpSecurity): SecurityFilterChain {
        http {
            formLogin { }                                    // 1차 등록은 기존 로그인으로
            webAuthn {
                rpName = "Book API"
                rpId = "bookapi.example.com"                 // 도메인과 일치해야 함 — localhost 개발 시 "localhost"
                allowedOrigins = setOf("https://bookapi.example.com")
            }
        }
        return http.build()
    }
}

기본 엔드포인트가 생깁니다: POST /webauthn/register/options → POST /webauthn/register(등록), POST /webauthn/authenticate/options → POST /login/webauthn(로그인). 기본 저장소는 인메모리이므로 운영에서는 JdbcPublicKeyCredentialUserEntityRepository·JdbcUserCredentialRepository를 빈으로 등록해 DB에 저장합니다(스키마는 Spring Security가 제공).

Phase 5-2 §6의 JWT 리소스 서버에서 권한 매핑을 위해 JwtAuthenticationConverter를 직접 만들던 코드가 4.1에서 프로퍼티로 내려왔습니다.

4.3 SSRF 방어 — InetAddressFilter

SSRF(Server-Side Request Forgery)는 사용자가 준 URL을 서버가 대신 fetch할 때, 그 URL이 http://169.254.169.254/(클라우드 메타데이터)나 http://10.0.0.5:5432(내부 DB)를 가리키는 공격입니다. §3의 에이전트 도구가 이 패턴을 정확히 만듭니다. Boot 4.1은 빈 하나로 자동 설정된 모든 HTTP 클라이언트(RestClient, WebClient, HTTP 인터페이스 클라이언트)에 주소 필터를 적용합니다.

kotlin
package com.example.bookapi.config

import org.springframework.context.annotation.Bean
import org.springframework.context.annotation.Configuration
// InetAddressFilter import — Boot 4.1 HTTP 클라이언트 자동 설정 모듈

@Configuration(proxyBeanMethods = false)
class HttpClientSecurityConfig {
    // 사설망·루프백·링크로컬(메타데이터 169.254.x.x)로 나가는 요청을 DNS 해석 후 차단 → FilteredHostException
    @Bean
    fun ssrfFilter(): InetAddressFilter = InetAddressFilter.externalAddresses()
}

필터는 Spring이 만들어 준 클라이언트에만 붙습니다. RestClient.create()로 직접 만든 인스턴스는 보호되지 않습니다 — §1의 추적과 같은 이유입니다. 이 가이드가 Phase 5-1부터 RestClient.Builder 주입을 고집한 이유가 하나 더 늘었습니다.

5. 판정 — 규모 단계별로

기술S0~S1S2S3한 줄 근거
OpenTelemetry 스타터채택채택채택비용은 의존성 한 줄, 얻는 것은 백엔드 이식성. Phase 5-3 설정을 대체
