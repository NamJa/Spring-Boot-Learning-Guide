Spring 핵심

Spring Framework 기반
IoC 컨테이너와 AOP를 핵심으로 하는 경량 애플리케이션 프레임워크. 2003년 등장했고 본 가이드 기준은 7.0.8. Spring Boot·Data·Security 등 모든 프로젝트가 이 위에 올라간다. Spring & Spring Boot 입문
Spring Boot 기반
Spring Framework를 관례에 따라 자동으로 설정해 주는 레이어. 새 프레임워크가 아니다. 자동 설정·스타터·내장 서버·Actuator를 더한다. 본 가이드 기준 4.1.0. Spring & Spring Boot 입문
IoC (Inversion of Control, 제어의 역전) 핵심
객체의 생성·조립·생명주기 제어권을 개발자가 아니라 프레임워크(컨테이너)가 갖는 것. Spring의 거의 모든 기능이 이 위에 얹힌다. IoC 컨테이너와 의존성 주입
DI (Dependency Injection, 의존성 주입) 핵심
IoC를 구현하는 구체적 기법. 필요한 협력 객체를 컨테이너가 넣어 준다. Kotlin에서는 주생성자 파라미터가 곧 주입 지점이라 @Autowired 조차 생략된다. IoC 컨테이너와 의존성 주입
Bean 핵심
Spring 컨테이너가 생성·관리하는 객체. @Component 계열 애너테이션(컴포넌트 스캔)이나 @Bean 메서드로 등록한다. IoC 컨테이너와 의존성 주입
ApplicationContext / BeanFactory
IoC 컨테이너의 인터페이스. BeanFactory는 최소 기능(생성·DI), ApplicationContext는 그 위에 이벤트·국제화·환경·AOP를 더한 실무용 상위 인터페이스. IoC 컨테이너와 의존성 주입
스테레오타입 애너테이션 (@Component · @Service · @Repository · @Controller)
모두 @Component의 특수화로 기능은 사실상 같고 역할을 드러내는 문서적 의미가 다르다. 예외로 @Repository는 DB 예외를 Spring 표준 예외로 변환하는 부가 기능이 있다. IoC 컨테이너와 의존성 주입
컴포넌트 스캔 (Component Scan)
@ComponentScan이 선언된 클래스의 패키지 이하를 훑어 스테레오타입 애너테이션이 붙은 클래스를 Bean으로 등록하는 과정. 진입점을 최상위 패키지에 두는 이유. 자동 설정과 스타터
Bean 스코프 (singleton · prototype · request · session)
Bean 인스턴스를 몇 개 만들고 얼마나 유지할지. 기본은 singleton(컨테이너당 1개)이므로 가변 상태를 두면 동시성 버그가 난다. Bean 생명주기와 스코프
@PostConstruct / @PreDestroy
의존성 주입이 끝난 직후(초기화) · 컨테이너 종료 직전(소멸)에 한 번 호출되는 콜백(jakarta.annotation). 무거운 초기화는 생성자가 아니라 여기에 둔다. Bean 생명주기와 스코프
ObjectProvider
singleton Bean이 prototype Bean을 매 호출마다 새로 얻어야 할 때 주입받는 조회 창구. getObject()가 그때그때 새 인스턴스를 준다. Bean 생명주기와 스코프
자동 설정 (Auto-configuration)
클래스패스에 무엇이 있는지 보고 합리적인 기본 Bean을 대신 등록하는 Spring Boot의 핵심 기능. 후보 목록은 각 jar의 META-INF/spring/…AutoConfiguration.imports에 있다. 자동 설정과 스타터
@ConditionalOnMissingBean 외 @Conditional 계열
자동 설정의 적용 조건. 특히 @ConditionalOnMissingBean은 "사용자가 직접 만들면 양보한다"는 뜻으로, 재정의 가능성을 보장하는 장치다. 자동 설정과 스타터
조건 평가 보고서 (Condition Evaluation Report)
--debug 또는 debug: true로 켜면 어떤 자동 설정이 왜 적용/미적용됐는지 출력된다. Actuator의 /actuator/conditions로도 볼 수 있다. 자동 설정과 스타터
스타터 (Starter)
한 기능에 필요한 의존성을 묶은 편의 패키지. 버전은 BOM이 관리하므로 적지 않는다. Boot 4에서 이름이 정리됐다(spring-boot-starter-webmvc 등). 자동 설정과 스타터
BOM (Bill of Materials)
검증된 의존성 버전 조합표. spring-boot-dependencies가 Spring·Kotlin·Jackson·JUnit 등 수백 개 버전을 고정해 준다. build.gradle.kts 해부
AOP (Aspect-Oriented Programming)
로깅·트랜잭션·보안처럼 여러 메서드를 가로지르는 횡단 관심사를 비즈니스 로직에서 분리하는 기법. Spring에서는 런타임 프록시로 구현된다. 부록 C. AOP와 프록시
프록시 (Proxy)
원본과 같은 타입의 대리 객체. 호출을 가로채 부가 기능을 수행한 뒤 원본에 위임한다. Spring의 @Transactional·@Cacheable·@Async가 모두 이 구조. 프록시와 동적 프록시
JDK 동적 프록시 vs CGLIB
전자는 인터페이스를 구현한 프록시(인터페이스 필수), 후자는 대상 클래스를 상속한 프록시(final 불가). Spring Boot 기본은 CGLIB. 프록시와 동적 프록시
Aspect · Pointcut · Advice · Join Point
차례로 모듈화 단위(@Aspect), 어디에 적용할지(표현식), 무엇을 언제 할지(@Around 등), 적용 가능 지점(Spring AOP에서는 메서드 실행)이다. Spring AOP 실전
어드바이스 5종 (@Around · @Before · @AfterReturning · @AfterThrowing · @After)
@Around만 ProceedingJoinPoint.proceed()로 원본 실행 여부·시점·결과까지 제어한다. proceed()를 부르지 않으면 원본이 아예 실행되지 않는다. Spring AOP 실전
자기 호출 (self-invocation)
같은 클래스 안에서 this.method()로 호출하면 프록시를 우회하므로 @Transactional·@LogExecution이 조용히 무시된다. AOP 디버깅 1순위 용의자. 함정과 내부 동작
ThreadLocal
스레드마다 독립된 저장소. Spring은 현재 트랜잭션·영속성 컨텍스트·보안 컨텍스트를 여기에 담는다. 다른 스레드로 넘기면 전파되지 않는다(Boot 4.1의 @Async는 자동 전파). 함정과 내부 동작

웹 · HTTP

REST API
리소스를 URL(명사)로, 행위를 HTTP 메서드로 표현하는 API 설계 관례. GET /api/getBooks 같은 동사형 URL은 지양한다. 서버 사이드 개발 입문
Stateless (무상태)
서버가 요청 간 상태를 기억하지 않는 성질. 덕분에 인스턴스를 수평 확장할 수 있고, Cloud Run의 scale-to-zero도 가능해진다. 서버 사이드 개발 입문
Spring MVC
서블릿 기반 동기·블로킹 웹 스택. 요청 1건당 스레드 1개(thread-per-request). 본 가이드가 선택한 스택. Spring MVC vs WebFlux
Spring WebFlux
Reactor 기반 리액티브·논블로킹 웹 스택. 반환 타입이 Mono/Flux(Kotlin은 suspend/Flow). 전 구간이 논블로킹일 때만 이점이 있다. Spring MVC vs WebFlux
가상 스레드 (Virtual Threads, Project Loom)
JDK 21 정식 기능. 매우 가벼운 스레드로 블로킹 시 OS 스레드를 양보한다. spring.threads.virtual.enabled=true 한 줄로 MVC의 동시성 한계를 크게 완화한다. Spring MVC vs WebFlux
서블릿 (Servlet) · 서블릿 컨테이너
HTTP 요청 하나를 처리하는 Java 표준 객체와 그 실행 환경. Spring Boot는 Tomcat 11.0.22(Servlet 6.1)를 내장하며 패키지는 jakarta.servlet.*. DispatcherServlet과 요청 처리 흐름
DispatcherServlet (프런트 컨트롤러)
모든 요청을 가장 먼저 받는 단일 서블릿. 직접 처리하지 않고 HandlerMapping/HandlerAdapter에 위임하고 결과를 응답으로 변환한다. DispatcherServlet과 요청 처리 흐름
HandlerMapping / HandlerAdapter
"누가 처리할지" 찾는 쪽과 "어떻게 호출할지" 아는 쪽. 애너테이션 컨트롤러는 RequestMappingHandlerMapping + RequestMappingHandlerAdapter 조합. DispatcherServlet과 요청 처리 흐름
아규먼트 리졸버 / 리턴값 핸들러
컨트롤러 메서드의 입력(@PathVariable·@RequestBody·Model …)을 채워 주고, 출력(본문 또는 뷰 이름)을 처리하는 확장 지점. DispatcherServlet과 요청 처리 흐름
HttpMessageConverter
요청 본문 ↔ 객체를 변환하는 컴포넌트. @RequestBody/@ResponseBody가 이것을 트리거한다. JSON은 Boot 4에서 Jackson 3 기반. DispatcherServlet과 요청 처리 흐름
@RestController vs @Controller
@RestController = @Controller + @ResponseBody. 전자는 반환값을 본문으로, 후자는 String 반환값을 뷰 이름으로 해석한다. @RestController 구현
ResponseEntity vs @ResponseStatus
상태 코드·헤더·본문을 코드로 세밀하게 제어할 때는 ResponseEntity(201 + Location, 204 등), 상태 코드만 고정하면 될 때는 애너테이션. @RestController 구현
DTO (Data Transfer Object)
계층 간 데이터 전달 전용 객체. 엔티티와 분리해 노출 범위·요청/응답 차이·검증 규칙·변경 격리를 확보한다. 이 가이드는 CreateBookRequest/UpdateBookRequest/BookResponse. DTO와 JSON 직렬화
Jackson 3
Boot 4의 기본 JSON 엔진. 패키지가 tools.jackson.*로 바뀌고 가변 ObjectMapper 대신 불변 JsonMapper를 쓴다. 애너테이션만 com.fasterxml.jackson.annotation에 남았다. DTO와 JSON 직렬화
jackson-module-kotlin
기본 생성자가 없는 Kotlin data class를 주생성자로 역직렬화하고, 기본값과 null 안정성을 존중하게 해 주는 모듈. Boot 4 좌표는 tools.jackson.module:jackson-module-kotlin. DTO와 JSON 직렬화
서블릿 필터 (Filter)
서블릿 컨테이너 영역에서 DispatcherServlet 바깥을 감싸는 장치. chain.doFilter() 호출 전후가 요청/응답 시점. 인코딩·요청 로깅·Spring Security가 여기 산다. 서블릿 필터와 스프링 인터셉터
스프링 인터셉터 (HandlerInterceptor)
DispatcherServlet 안에서 컨트롤러 전후에 개입한다(preHandle/postHandle/afterCompletion). 어떤 핸들러가 실행될지 알고, 경로 패턴 제어가 유연하다. 서블릿 필터와 스프링 인터셉터
SSR (Server-Side Rendering) · Thymeleaf
서버가 완성된 HTML을 내려주는 방식과 그 표준 템플릿 엔진(3.1.5). templates/에 두고 Model로 데이터를 넘긴다. JSP는 실행 가능 jar와 궁합이 나빠 다루지 않는다. Thymeleaf 서버 사이드 렌더링
PRG (Post-Redirect-Get)
폼 저장 후 redirect:로 GET 페이지로 보내는 패턴. 새로고침 시 POST 재전송(중복 저장)을 막는다. Thymeleaf 서버 사이드 렌더링
쿠키 · 세션 · JSESSIONID
쿠키는 클라이언트 저장(위조 가능), 세션은 서버 보관 + 열쇠(세션 ID)만 쿠키로 전달. Servlet 관례상 그 쿠키 이름이 JSESSIONID. 쿠키·세션과 로그인
@SessionAttribute
세션 값을 컨트롤러 파라미터로 바로 주입받는 애너테이션. session.getAttribute() + 캐스팅을 대신한다. 쿠키·세션과 로그인

데이터 · JPA

ORM · 임피던스 불일치
객체와 테이블을 자동으로 매핑하는 기술, 그리고 참조 vs 외래 키·상속 유무 등 둘 사이의 근본적 차이. Spring Data JPA 개념
JPA · Hibernate · Spring Data JPA
차례로 표준 명세(jakarta.persistence.*), 구현체(본 가이드 7.4.1), Repository 추상화. Spring Data JPA를 써도 아래에서는 Hibernate가 SQL을 만든다. Spring Data JPA 개념
영속성 컨텍스트 (Persistence Context)
엔티티를 보관하는 논리적 작업 공간. 1차 캐시·동일성 보장·변경 감지·쓰기 지연이 모두 여기서 나온다. 수명은 트랜잭션과 같다. 영속성 컨텍스트
EntityManager
영속성 컨텍스트를 관리하는 주체. @PersistenceContext로 주입되는 것은 실제로 프록시라, 싱글턴 빈에 주입해도 스레드별 트랜잭션마다 다른 컨텍스트를 쓴다. 영속성 컨텍스트
엔티티 생명주기 (비영속 · 영속 · 준영속 · 삭제)
transient → persist() → managed → detach()/clear() → detached, remove() → removed. 영속 상태에서만 변경 감지가 동작한다. 영속성 컨텍스트
1차 캐시 · 동일성 보장
같은 트랜잭션에서 같은 ID를 두 번 조회하면 DB에 가지 않고 같은 인스턴스를 반환한다(a === b). 애플리케이션 전역 2차 캐시와 다르다. 영속성 컨텍스트
변경 감지 (Dirty Checking)
적재 시 저장한 스냅샷과 현재 상태를 flush 시점에 비교해 UPDATE를 자동 생성한다. 그래서 save() 없이 필드만 바꿔도 수정이 반영된다. 영속성 컨텍스트
쓰기 지연 (Write-behind) · flush
SQL을 모아 두었다가 flush(커밋 직전·JPQL 실행 직전·수동 호출) 시점에 전송한다. flush는 컨텍스트를 비우지 않는다. 영속성 컨텍스트
merge()
준영속 엔티티의 값을 복사해 새 영속 인스턴스를 반환한다(인자 객체는 그대로 준영속). 모든 필드를 덮어써 null 유실 위험이 있어 "조회 후 변경 감지" 패턴이 권장된다. 영속성 컨텍스트
@Entity · @Table · @Id · @Column
클래스=테이블, 인스턴스=행, 프로퍼티=컬럼 매핑을 선언하는 기본 애너테이션. Kotlin에서는 data class를 피하고 일반 class + var + id 기반 equals/hashCode로 만든다. Entity 매핑 (Kotlin)
@GeneratedValue (IDENTITY · SEQUENCE · AUTO)
PK 생성 전략. 본 가이드는 IDENTITY(DB auto-increment). 단 IDENTITY는 ID를 알기 위해 즉시 INSERT하므로 쓰기 지연·배치가 사실상 무력화된다. Entity 매핑 (Kotlin)
@Enumerated(EnumType.STRING)
enum을 이름으로 저장. 기본값 ORDINAL(순서 정수)은 상수를 중간에 추가하면 기존 데이터의 의미가 뒤바뀌므로 항상 STRING을 명시한다. 상속 매핑과 값 타입
연관관계의 주인 · mappedBy
테이블에는 FK가 하나뿐이므로 객체 참조 둘 중 하나만 FK를 관리한다. 규칙: FK를 가진 @ManyToOne 쪽이 주인, 반대쪽은 mappedBy로 거울임을 선언. 연관관계 매핑
연관관계 편의 메서드
양방향 연관에서 주인 쪽 FK 세팅을 빼먹지 않도록 양쪽을 한 번에 맞추는 메서드(addReview()). 한쪽에만 두고, toString/equals에 양방향 필드를 넣지 않는다. 연관관계 매핑
cascade · orphanRemoval
부모의 영속성 동작을 자식에게 전파 / 컬렉션에서 빠진 자식을 자동 삭제. 자식이 그 부모에게만 속할 때만 켠다(공유되는 Category에는 금지). 연관관계 매핑
상속 매핑 (SINGLE_TABLE · JOINED · TABLE_PER_CLASS)
한 테이블에 몰아넣기 / 부모·자식 테이블 분리 후 조인 / 자식마다 독립 테이블. 기본은 SINGLE_TABLE, NOT NULL이 중요하면 JOINED, 마지막은 비권장. 상속 매핑과 값 타입
@MappedSuperclass · JPA Auditing
테이블 없이 컬럼 매핑 정보만 물려주는 부모. @CreatedDate/@LastModifiedDate + @EnableJpaAuditing으로 생성·수정 시각을 자동 기록한다. 상속 매핑과 값 타입
값 타입 (@Embeddable · @Embedded)
식별자가 없는 값 묶음(주소·금액)을 소속 엔티티 테이블의 컬럼들로 펼친다. 인스턴스를 공유하지 말고 통째로 교체하는 식으로 다룬다. 상속 매핑과 값 타입
지연 로딩 (FetchType.LAZY) vs 즉시 로딩 (EAGER)
연관 객체 자리에 프록시를 두고 실제 접근 시 조회 / 조회 즉시 함께 로딩. @ManyToOne·@OneToOne의 기본값이 EAGER라 전부 LAZY로 명시하는 것이 정석. 프록시와 즉시/지연 로딩, N+1
N+1 문제
목록 조회 1번 + 각 행의 연관 초기화 N번으로 쿼리가 폭증하는 현상. EAGER로 바꿔도 해결되지 않는다(횟수 동일). 본질은 "한 번에 가져오지 않는 것". 프록시와 즉시/지연 로딩, N+1
페치 조인 (fetch join) · @EntityGraph
연관을 한 방의 JOIN으로 함께 로딩하는 JPQL 문법과 그 선언적 버전. 컬렉션 페치 조인 + 페이징은 메모리 페이징 경고가 나므로 배치 페치로 푼다. 프록시와 즉시/지연 로딩, N+1
@BatchSize · default_batch_fetch_size
연관 초기화를 IN 절로 묶어 N번을 몇 번으로 줄인다. 전역 설정(100~1000)을 기본으로 켜 두는 것이 실무 권장. 프록시와 즉시/지연 로딩, N+1
OSIV (Open Session In View)
영속성 컨텍스트를 HTTP 응답 끝까지 살려 두는 옵션(spring.jpa.open-in-view, 기본 true). 편리하지만 DB 커넥션 점유 시간이 길어져 고트래픽에서는 끄는 것을 권장. 프록시와 즉시/지연 로딩, N+1
LazyInitializationException
트랜잭션(=컨텍스트)이 닫힌 뒤 지연 로딩 필드에 접근할 때 발생. 해법은 트랜잭션 안에서 미리 로딩하거나 DTO로 변환해 반환하는 것. 트랜잭션 관리
JpaRepository · 파생 쿼리 (Derived Query)
인터페이스만 선언하면 CRUD 구현이 생기고, findByAuthorAndPriceLessThan처럼 메서드 이름을 파싱해 쿼리를 만들어 준다. Repository 인터페이스
Page · Slice · Pageable · Sort
페이징 3종. Page는 전체 개수를 위해 count 쿼리를 추가로 실행하고, Slice는 다음 페이지 유무만 확인해 더 가볍다. Repository 인터페이스
findByIdOrNull
findById(id).orElse(null)의 Kotlin 확장(org.springframework.data.repository). Optional을 nullable 타입으로 바꿔 준다. Repository 인터페이스
트랜잭션 · @Transactional
여러 DB 작업을 원자적 단위로 묶는다. 서비스 계층에 붙이고, import는 org.springframework.transaction.annotation을 쓴다(Spring 옵션을 쓰기 위해). 트랜잭션 관리
readOnly = true
조회 전용 트랜잭션. 변경 감지 스냅샷을 만들지 않아 메모리·CPU를 아끼고 불필요한 flush를 막는다. 클래스에 깔고 쓰기 메서드만 재정의하는 패턴이 흔하다. 트랜잭션 관리
전파 (Propagation) · 격리 수준 (Isolation)
기존 트랜잭션이 있을 때의 동작(REQUIRED 기본, REQUIRES_NEW 등)과 동시 트랜잭션의 간섭 정도(대개 DB 기본값 유지). 트랜잭션 관리
롤백 규칙
unchecked 예외는 롤백, checked 예외는 커밋이 기본. Kotlin에는 checked 예외가 없어 대개 "예외 발생 시 롤백"으로 이해하면 된다. 예외를 try-catch로 삼키면 롤백되지 않는다. 트랜잭션 관리
ddl-auto (none · validate · update · create · create-drop)
기동 시 스키마 처리 전략. 개발은 create-drop/update, 운영은 validate(또는 none) + 마이그레이션 도구가 정석. 데이터베이스 설정
Flyway · Liquibase
스키마 변경을 버전 관리하는 마이그레이션 도구. Flyway는 V1__init.sql처럼 SQL 파일을 순서대로 적용한다(Boot 4.1 관리 버전 12.4). 데이터베이스 설정
HikariCP
Spring Boot 기본 JDBC 커넥션 풀(관리 버전 7.0). 커넥션 점유 시간이 길어지면 풀 고갈로 이어지므로 OSIV·트랜잭션 범위 설계와 직결된다. Spring Data JPA 개념

쿼리 · Querydsl

JPQL (Jakarta Persistence Query Language)
테이블이 아니라 엔티티와 필드를 대상으로 하는 객체 지향 쿼리 언어. select b from Book b where b.price >= :min 처럼 쓰고 별칭이 필수다. JPQL
프로젝션 (엔티티 · 스칼라 · DTO)
select 절에 무엇을 담을지. DTO 프로젝션은 JPQL의 new 패키지.DTO(...) 구문을 쓰는데 FQCN과 생성자 순서를 손으로 맞춰야 해 깨지기 쉽다. JPQL
벌크 연산 (@Modifying · executeUpdate())
여러 행을 한 번에 수정/삭제. 영속성 컨텍스트를 거치지 않고 DB에 직접 나가므로 1차 캐시가 어긋난다. 직후 clear() 또는 @Modifying(clearAutomatically = true)가 필요. JPQL
Querydsl
코드로 타입 안전한 쿼리를 작성하는 라이브러리. 오타가 컴파일 에러가 되고 동적 쿼리를 우아하게 조립한다. 현재 표준은 OpenFeign 포크(io.github.openfeign.querydsl 7.5). 왜 Querydsl인가
Q타입 (QBook)
엔티티로부터 빌드 시점에 생성되는 쿼리용 메타 클래스. 보통 정적 인스턴스 QBook.book을 쓰고, 자기 조인 등에는 QBook("sub")처럼 별칭을 만든다. Kotlin + Gradle 설정
JPAQueryFactory
Querydsl 쿼리의 진입점. EntityManager를 받아 빈으로 등록해 두고 주입받아 쓴다. 패키지는 group id와 무관하게 com.querydsl.jpa.impl. Kotlin + Gradle 설정
BooleanExpression · BooleanBuilder
동적 쿼리의 두 방식. where(...)는 null 인자를 무시하므로 "조건 없으면 null 반환" 메서드를 나열하는 쪽이 권장되고, 복잡한 and/or 그룹핑에는 BooleanBuilder가 편하다. 동적 쿼리와 조인
fetchJoin() · JPAExpressions
Querydsl에서 N+1을 푸는 페치 조인과 서브쿼리 빌더. JPQL 표준상 from 절 서브쿼리는 지원되지 않는다. 동적 쿼리와 조인
Projections · @QueryProjection
DTO로 결과를 받는 두 방법. Projections.constructor는 순서를 런타임에 검증하고, @QueryProjection은 DTO의 Q타입을 만들어 컴파일 타임에 검증한다(대신 DTO가 Querydsl에 의존). DTO 프로젝션 & 리포지토리 통합
사용자 정의 리포지토리 (…Custom / …Impl)
Spring Data 기본 기능과 Querydsl 구현을 하나의 인터페이스로 합치는 표준 패턴. 구현 클래스 이름은 반드시 [리포지토리명]Impl. DTO 프로젝션 & 리포지토리 통합

검증 · 설정 · 예외

Bean Validation · Hibernate Validator
필드에 제약을 선언하면 런타임에 검사해 주는 표준 명세(jakarta.validation.*)와 그 구현체. Boot 4에서는 spring-boot-starter-validation을 직접 추가해야 한다. Bean Validation 입력 검증
@NotNull · @NotEmpty · @NotBlank
차례로 null만 / null·빈 값 / null·빈 문자열·공백까지 거부. 문자열 필수값에는 거의 항상 @NotBlank. Bean Validation 입력 검증
@field: use-site target
Kotlin에서 애너테이션을 백킹 필드에 붙이도록 지정하는 표기. 검증기가 읽는 자리라서 예전에는 필수였다. Initializr 기본 옵션(-Xannotation-default-target=param-property)이 켜져 있으면 생략해도 동작한다. Bean Validation 입력 검증
@Valid vs @Validated
전자는 표준으로 @RequestBody 검증·중첩 객체를 지원하고, 후자는 Spring 전용으로 검증 그룹과 메서드 파라미터 검증(클래스에 부착)을 지원한다. Bean Validation 입력 검증
MethodArgumentNotValidException / HandlerMethodValidationException
본문(@Valid @RequestBody) 검증 실패 / 파라미터 레벨(@Validated + @PathVariable 등) 검증 실패 시 던져지는 예외. 전역 처리 시 둘 다 고려한다. Bean Validation 입력 검증
커스텀 검증기 (@Constraint · ConstraintValidator)
표준 애너테이션으로 표현 못 하는 규칙(예: ISBN 체크섬)을 직접 만드는 방법. message·groups·payload 세 멤버는 명세상 필수. Bean Validation 입력 검증
@RestControllerAdvice · @ExceptionHandler
컨트롤러에서 던져진 예외를 한곳에서 잡아 의미 있는 상태 코드·본문으로 바꾸는 장치. ResponseEntityExceptionHandler를 상속하면 MVC 표준 예외도 함께 처리된다. 전역 예외 처리
ProblemDetail (RFC 9457)
HTTP API 에러의 표준 형태(type·title·status·detail·instance + 확장 필드). 반환하면 application/problem+json으로 직렬화된다. 신규 프로젝트 권장. 전역 예외 처리
외부화된 설정 (Externalized Configuration)
설정값을 코드에서 분리해 환경마다 주입하는 원칙. 우선순위는 커맨드라인 > 환경 변수 > application-{profile}.yml > application.yml > 코드 기본값. 외부화된 설정과 프로파일
프로파일 (Profile) · 프로파일 그룹
환경별 설정 묶음(dev·prod·test)과 여러 프로파일을 한 이름으로 켜는 기능. @Profile("!prod")처럼 Bean 등록도 갈라낼 수 있다. 외부화된 설정과 프로파일
느슨한 바인딩 (Relaxed Binding)
app.book.default-page-size = defaultPageSize = 환경 변수 APP_BOOK_DEFAULTPAGESIZE 를 같은 키로 취급하는 규칙. 컨테이너 환경 변수 주입의 기반. 외부화된 설정과 프로파일
플레이스홀더 ${VAR:기본값}
환경 변수가 있으면 그 값, 없으면 기본값. 비밀번호처럼 기본값을 두면 위험한 항목은 일부러 비워 기동 실패로 만드는 것이 안전하다. 외부화된 설정과 프로파일
@ConfigurationProperties vs @Value
관련 설정을 타입 안전한 클래스에 통째로 바인딩 vs 단일 값 주입. 전자는 느슨한 바인딩·검증·중첩 타입에 강하고, 후자는 SpEL을 쓸 수 있다. @ConfigurationProperties
생성자 바인딩 · @EnableConfigurationProperties / @ConfigurationPropertiesScan
val만 가진 불변 data class로 설정을 받는 권장 방식과, 그 클래스를 빈으로 등록하는 두 가지 방법(@Component는 쓸 수 없다). @ConfigurationProperties
configuration-processor
설정 메타데이터를 만들어 IDE 자동완성을 돕는 애너테이션 프로세서. Kotlin에서는 kapt로만 동작하며(KSP 미지원), 기본값 탐지 등 일부 기능에 제약이 있다. @ConfigurationProperties

Spring Security
인증·인가 프레임워크(본 가이드 7.1.0). 스타터만 추가해도 모든 엔드포인트가 잠기는 secure-by-default 철학. 내부는 거대한 서블릿 필터 체인. Spring Security 7 기초
SecurityFilterChain
"어떤 경로에 어떤 인증·인가 규칙을 적용할지" 담은 필터 묶음. Security 7에서는 WebSecurityConfigurerAdapter 상속이 아니라 이 빈을 등록하는 방식만 쓴다. Spring Security 7 기초
Security Kotlin DSL (http { })
람다 빌더보다 읽기 좋은 Kotlin 전용 설정 DSL. import org.springframework.security.config.annotation.web.invoke 확장을 빼먹으면 컴파일되지 않는다. Spring Security 7 기초
인증 (Authentication) vs 인가 (Authorization)
"누구인가"를 확인하는 것과 "무엇을 할 수 있는가"를 판단하는 것. 전자는 인증 필터(Basic·폼·JWT), 후자는 authorizeHttpRequests·@PreAuthorize가 담당. Spring Security 7 기초
PasswordEncoder · BCrypt
비밀번호를 단방향 해시로 저장하기 위한 추상화와 그 표준 구현. 평문 저장은 금지이며 BCryptPasswordEncoder가 기본 선택. Spring Security 7 기초
CSRF (Cross-Site Request Forgery)
브라우저가 자동 전송하는 쿠키 세션을 악용하는 공격. 쿠키 세션 + 서버 렌더링 폼이면 반드시 켜고, 헤더 토큰 기반 순수 REST API면 끌 수 있다. Spring Security 7 기초
OAuth2 Resource Server · JWT
우리 API가 인증 서버(Keycloak·Auth0 등)가 발급한 토큰을 검증만 하는 역할. issuer-uri 하나로 서명·만료 검증이 자동 구성된다. 운영 REST API의 정석. Spring Security 7 기초
메서드 보안 (@EnableMethodSecurity · @PreAuthorize)
URL 규칙 외에 서비스 메서드 단위로 인가를 표현하는 방법. 비즈니스 규칙 가까이에서 권한을 선언할 수 있다. Spring Security 7 기초
SSRF 완화 (InetAddressFilter)
Boot 4.1 신규. HTTP 클라이언트가 내부망 등 허용되지 않은 주소로 나가는 것을 차단한다. 사용자 입력으로 URL을 만드는 기능이 있으면 검토. 선언적 HTTP 클라이언트
Secret Manager · Workload Identity Federation (WIF)
비밀값을 외부 금고에서 주입하는 방식과, JSON 키 없이 GitHub 워크플로 신원을 GCP가 직접 신뢰하게 하는 인증 방식. 장기 비밀이 없어 더 안전하다. CI/CD와 운영

관측성 · 테스트

Actuator
헬스·메트릭·환경·로거 등을 즉시 사용 가능한 엔드포인트로 노출하는 운영 모듈. 기본 노출은 health뿐이며 필요한 것만 열어야 한다. Actuator와 관측성
liveness / readiness 프로브
"프로세스가 살아 있나"(실패 시 재시작) vs "트래픽을 받을 준비가 됐나"(실패 시 트래픽 제외). management.endpoint.health.probes.enabled=true로 그룹을 켠다. Actuator와 관측성
HealthIndicator
헬스 체크 항목 하나를 구현하는 인터페이스. Boot 4에서 패키지가 org.springframework.boot.health.contributor로 이동했다. Actuator와 관측성
Micrometer · MeterRegistry
"메트릭계의 SLF4J". 코드는 Micrometer API로 쓰고 백엔드(Prometheus·OTLP)는 의존성만 갈아끼운다. Counter·Timer를 MeterRegistry에 등록해 쓴다. Actuator와 관측성
Prometheus · Grafana
/actuator/prometheus를 주기적으로 스크레이프해 시계열로 저장하는 수집기와, 그것을 그리는 대시보드. Actuator와 관측성
분산 추적 · OpenTelemetry (OTLP)
요청 하나가 어디서 시간을 썼는지 구간(span)별로 보는 기법과 그 표준·전송 프로토콜. Micrometer Tracing이 브리지 역할을 한다. Actuator와 관측성
구조화 로깅 (Structured Logging)
로그를 JSON으로 출력해 수집기가 필드 단위로 파싱하게 하는 것. Boot 4 내장 기능(logging.structured.format.console=ecs)이며 trace ID와 엮어 쓴다. Actuator와 관측성
관측성 3대 신호 (Metrics · Traces · Logs)
무엇이 얼마나 / 어디서 느린가 / 정확히 무슨 일이. 셋을 trace ID 하나로 연결하는 것이 운영 디버깅의 핵심. Actuator와 관측성
테스트 슬라이스
필요한 만큼만 컨텍스트를 띄우는 전략. @WebMvcTest(웹) · @DataJpaTest(JPA) · @RestClientTest(외부 호출) · @SpringBootTest(전체). 좁은 것 많이, 통합은 적게. 테스트 전략
@MockitoBean
스프링 컨텍스트의 빈을 목으로 교체하는 애너테이션. Boot 4에서 @MockBean·@SpyBean은 제거되어 이것으로 대체됐다. 테스트 전략
MockMvc · MockMvcTester
서버 없이 웹 계층을 호출하는 테스트 도구와, 그 AssertJ 기반 fluent 버전. Kotlin에서는 mockMvc.get("/api/books") { … } DSL도 쓸 수 있다. 테스트 전략
RestTestClient
Spring Framework 7의 테스트용 HTTP 클라이언트. @SpringBootTest(RANDOM_PORT) + @AutoConfigureRestTestClient로 주입받아 exchange().expectStatus() 체인으로 검증한다. 테스트 전략
Testcontainers · @ServiceConnection
테스트 중 실제 DB를 도커로 띄우는 도구와, 그 접속 정보를 datasource 설정에 자동 연결해 주는 애너테이션. 2.x에서 아티팩트·클래스 패키지가 바뀌었다. 테스트 전략
MockRestServiceServer
외부 API 호출을 실제 서버 없이 흉내 내는 테스트 서버. @RestClientTest 슬라이스가 RestClient.Builder에 끼워 준다. 테스트 전략

빌드 · 배포 · 클라우드

실행 가능 jar (fat jar) · bootJar
애플리케이션과 모든 의존성을 한 jar에 담아 java -jar로 바로 실행되는 산출물. Main-Class는 JarLauncher이며 plain jar와는 용도가 다르다. 실행 가능 JAR 빌드
layered jar · -Djarmode=tools
jar 내부를 변경 빈도에 따라 4개 레이어(dependencies · spring-boot-loader · snapshot-dependencies · application)로 나눈 구조와, 그것을 추출하는 도구 모드. 실행 가능 JAR 빌드
Cloud Native Buildpacks · Paketo · bootBuildImage
Dockerfile 없이 소스/jar를 분석해 OCI 이미지를 만들어 주는 표준과 그 구현, 그리고 이를 실행하는 Gradle 태스크. OS 패치를 빌드팩 업데이트로 흡수한다. Docker 컨테이너화
멀티 스테이지 빌드
빌드 단계에서만 JDK·Gradle을 쓰고 런타임 이미지에는 JRE와 산출물만 남기는 Dockerfile 기법. 레이어 분리와 함께 이미지 크기·캐시 효율을 좌우한다. Docker 컨테이너화
-XX:MaxRAMPercentage
컨테이너에 할당된 메모리의 비율로 힙 상한을 정하는 JVM 옵션. 고정 -Xmx보다 안전하다(JDK 21은 cgroup 한도를 자동 인식). 실행 가능 JAR 빌드
AOT · GraalVM 네이티브 이미지
빌드 시점에 기계어로 컴파일해 JVM 없이 실행되는 단일 파일을 만드는 기술. 시작 수십 ms·메모리 수십 MB이지만 빌드가 길고 closed-world 제약이 있다. GraalVM 네이티브 이미지
런타임 힌트 (@RegisterReflectionForBinding · RuntimeHintsRegistrar)
네이티브 이미지가 리플렉션·프록시·리소스를 알 수 있게 빌드 시점에 알려 주는 메타데이터. 네이티브에서만 나는 오류의 대부분이 힌트 누락이다. GraalVM 네이티브 이미지
12-factor · 그레이스풀 셧다운
"설정은 코드와 분리해 환경에 둔다"는 원칙과, SIGTERM 후 진행 중 요청을 마무리하고 종료하는 동작(Boot 4는 기본 활성화). 무중단 배포의 전제. 프로파일별 배포 & 운영
Cloud Run
컨테이너 기반 서버리스 플랫폼. HTTPS URL·오토스케일링·요청 기반 과금을 제공하고 트래픽이 없으면 인스턴스를 0으로 줄인다. Cloud Run 핵심 개념
Service · Revision · Instance
고정 URL을 갖는 배포 단위 / 이미지+설정의 불변 스냅샷 / 실제 실행 컨테이너. 리비전 단위로 롤백·트래픽 분할(카나리)이 가능하다. Cloud Run 핵심 개념
동시성 (Concurrency) · 콜드 스타트
인스턴스 하나가 동시에 처리하는 요청 수(gcloud 배포 기본 = vCPU × 80)와, 인스턴스가 0인 상태에서 처음 요청이 겪는 기동 지연. --min-instances·--cpu-boost·네이티브 이미지로 완화한다. Cloud Run 핵심 개념
scale to zero · 무료 티어
트래픽이 없으면 인스턴스를 0개로 줄여 비용이 0에 수렴하는 성질과, 결제 계정당 월 200만 요청·180,000 vCPU-초·360,000 GiB-초의 무료 한도. Cloud Run 핵심 개념
PORT 환경 변수
Cloud Run이 컨테이너에 주입하는 리스닝 포트. Spring Boot는 PORT를 알지 못하므로 server.port: ${PORT:8080}으로 직접 연결해야 한다(가장 흔한 배포 실패 원인). 소스에서 직접 배포
Artifact Registry · Cloud Build
GCP의 컨테이너 이미지 저장소와 빌드 서비스. --source 배포는 Cloud Build가 (Dockerfile 또는 buildpacks로) 이미지를 만들어 여기에 올린다. 컨테이너 이미지 빌드 후 배포
Cloud SQL · 휘발성 파일 시스템
관리형 관계형 DB와, Cloud Run 인스턴스의 인메모리 파일 시스템. 디스크에 쓴 내용은 사라지고 메모리를 잡아먹으므로 영구 데이터는 Cloud SQL·Cloud Storage에 둔다. CI/CD와 운영

Kotlin · 빌드 도구

kotlin-spring (all-open)
Kotlin 클래스는 기본이 final이라 CGLIB 프록시를 만들 수 없다. 이 플러그인이 @Component·@Transactional 등이 붙은 클래스를 자동으로 open 처리해 준다. build.gradle.kts 해부
kotlin-jpa (noArg) · allOpen 블록
@Entity에 JPA가 요구하는 기본 생성자를 합성하는 플러그인. Initializr는 함께 allOpen { annotation("jakarta.persistence.Entity") … } 블록도 생성한다. Entity 매핑 (Kotlin)
-Xjsr305=strict
Java API의 nullability 애너테이션을 엄격히 해석해, 플랫폼 타입 대신 정확한 null 가능/불가능 타입으로 다루게 하는 컴파일러 옵션. build.gradle.kts 해부
-Xannotation-default-target=param-property
주생성자 프로퍼티의 애너테이션을 파라미터와 프로퍼티(필드)에 함께 적용하는 Kotlin 2.2+ 옵션. Initializr 기본값이며 Kotlin 2.4부터는 언어 기본 동작. Bean Validation 입력 검증
kapt vs KSP
Kotlin에서 애너테이션 프로세서를 돌리는 두 방식. kapt는 Java stub을 거쳐 느리지만 검증돼 있고(현재 유지보수 모드), KSP는 Kotlin 네이티브로 빠르다. Querydsl은 양쪽 다 지원. Kotlin + Gradle 설정
Gradle Wrapper · 툴체인 (toolchain)
저장소에 포함된 스크립트로 고정된 Gradle 버전을 쓰게 하는 장치와, 빌드 머신의 기본 JDK와 무관하게 특정 JDK로 컴파일하도록 고정하는 설정. 개발 환경 설정
Spring Initializr
start.spring.io의 프로젝트 생성기. 웹·curl·IntelliJ에서 모두 쓸 수 있고, 본 가이드의 build.gradle.kts는 여기 출력을 기준으로 검증했다. Spring Initializr로 프로젝트 생성
DevTools
클래스 변경 시 애플리케이션을 자동 재시작해 주는 개발 편의 모듈(developmentOnly 스코프라 운영 산출물에는 빠진다). 재시작하면 메모리 데이터는 초기화된다. 로컬 실행과 테스트
